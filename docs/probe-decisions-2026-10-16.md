# Пробник decision-моделей через OpenRouter — 2026-10-16

Шаг T1 [RFC 21](../proposals/21-decision-models-shadow.md): подтвердить API до того, как
писать под него Rust. Метод — `bin/pr-review-probe-decisions.mjs` (сырой fetch), две модели ×
~10 вызовов, плюс отдельная проверка «перестановки как вопросы одного вызова». Суммарная
стоимость замера < $0.002.

## Итог: K0 не сработал, обе модели в эксперименте

Обе модели обслуживаются **одним** эндпоинтом с одной схемой — отдельный «формат OpenAI»
не нужен, переменная `REVIEW_DECISION_FORMAT` из плана выброшена.

```
POST https://openrouter.ai/api/alpha/decisions
{ "model": "...", "state": <string|object|array>,
  "questions": { "<name>": { "type": "choice", "instructions": "...",
                             "criteria": { "<value>": "<описание>", ... } } } }
→ { "model": "...-<дата>", "provider": "...",
    "answers": { "<name>": { "type": "choice", "choice": "<value>",
                             "probabilities": { "<value>": p, ... }, "confidence": c } },
    "usage": { "input_tokens": n, "output_tokens": m, "cost": $ } }
```

Типы вопросов: `choice` (criteria — объект value→описание), `noul` (criteria `{true,false}`,
ответ — число `noul`), `score` (criteria — массив уровней), `box` (картинки). Несколько
вопросов в одном вызове — да, вход читается один раз. Ошибка схемы — `400` с zod-описанием
пути. `usage.cost` приходит в ответе — цену можно брать оттуда, а не из прайса.

## Замер

Вход Q1 — находка + фрагмент диффа, 10 вариантов (семейства FP 1–8, `other_fp`, `real`).

| | `microsoft/microsoft-decision-1` | `openai/gpt-6-luna-decisions` |
|---|---|---|
| Провайдер / снапшот | Azure / `-20261009` | OpenAI / `-20261006` |
| Реальная находка (off-by-one) | `real` 0.75, conf 0.72 | `real` 0.89, conf 0.88 |
| FP «теста нет в PR» (тест в диффе) | `f1_in_diff` 0.996 | `f1_in_diff` 0.97 |
| Повтор ×3, max TV | **0.044** — не детерминирована | **0** — детерминирована |
| Обратный порядок вариантов, TV | 0.10 (argmax тот же) | 0.07 (argmax тот же) |
| Сетка вероятностей | непрерывная | **шаг 0.01** |
| `noul` «реальный дефект?» | 0.80 | **1.0** — насыщение |
| Латентность, холодный / тёплый | 1.5 с / 0.37–0.57 с | 1.2 с / 0.37–0.43 с |
| Вход 4K / 16K символов | 365 / 566 мс | 412 / 433 мс |
| Цена вызова Q1 (~360–460 ток.) | $0.000015 | $0.000046 |
| $/1M входа (по `usage.cost`) | 0.042 | 0.10 |

**Перестановки внутри одного вызова** (тот же вход, вопросы `p0`/`p1` с обратным порядком
criteria):

| | отдельные вызовы p0 / p1 | один вызов p0 / p1 |
|---|---|---|
| Decision-1 | `a_bug` 0.824 / 0.855 | 0.870 / 0.870 — **совпадают до 16 знаков** |
| Luna | 0.99 / 0.99 | 0.99 / 0.99 |

## Что это значит для реализации

1. **Перестановки — только отдельными вызовами.** У Decision-1 два вопроса с разным порядком
   в одном вызове дают побитово одинаковый ответ: сервер, по-видимому, канонизирует порядок
   вариантов внутри вызова (или кэширует оценку по множеству вариантов). Для замера смещения
   порядка это бесполезно.
2. **У Decision-1 шум повтора (TV ≈ 0.04) сравним с эффектом порядка (TV ≈ 0.10).** Офлайн-замер
   обязан разделять их: K повторов на одном порядке против K перестановок, иначе «смещение
   порядка» окажется шумом сэмплинга.
3. **Luna отдаёт вероятности на сетке 0.01 и насыщает `noul`.** Нижняя граница разрешения —
   0.01; AUC по `p(real)` у неё будет с большим числом связей. Для порога это хуже, чем у
   Decision-1; для argmax-согласия не мешает.
4. **Цена несущественна:** при 40 вызовах на прогон — $0.0006 (Decision-1) и $0.0018 (luna).
   Потолок `REVIEW_DECISION_MAX_CALLS` нужен против латентности и rate-limit, а не против денег.
5. **Холодный первый вызов ~1.3 с** — shadow стартует параллельно engine, в хвост прогона это
   не попадает.

Неподтверждённым осталось: поведение на 402/429 (не воспроизвести без исчерпания), лимит числа
вариантов (нам нужно ≤ 10 — проверено), стабильность эндпоинта во времени (`alpha` в пути).
