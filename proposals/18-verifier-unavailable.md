# 18 — Сбой verifier'а: одно состояние вместо исхода по виду сбоя

> Категория: 🎯 Прямое · Риск: средний · Зависимости: RFC 17 (батчи verifier), `REVIEW_LLM_REQUIRED` (образец fail-closed)

## Контекст

Гейт обещает блок только с вердиктом второго судьи (CLAUDE.md, «Два независимых судьи»).
Когда verifier не отвечает, этого вердикта нет, и решать приходится без него. Сейчас решение
зависит не от политики, а от того, как именно verifier сломался.

## Текущее состояние

Прогон всего `run()` с одной находкой critical (confidence 0.9) через DI-пайплайн, дефолты:

| Путь | exit | Sticky |
|---|---|---|
| verified | 1 | «подтверждено 1» |
| исключение первого вызова (сеть, 5xx, таймаут) | 1 | строки verifier нет — блок выглядит подтверждённым |
| пустой ответ `[]` | 0 | «без подтверждения → minor» |
| вердикты с чужими индексами | 0 | то же |
| тайм-бюджет < 2 мин перед стадией | 1 | строки verifier нет |
| `REVIEW_VERIFIER=0` | 1 | строки нет (выбор потребителя) |

Причины по коду (`pipeline.mjs`, `runVerifierStage`): исключение и тайм-бюджет возвращают
находки нетронутыми (`return empty`), и non-strict гейт блокирует по confidence агрегатора;
пустой ответ доходит до `applyVerifierVerdicts`, где при `REVIEW_VERIFIER_STRICT=1` каждый
кандидат без вердикта понижается до minor. Баннер sticky при этом обещает «Инфра-сбои merge
не блокируют» — неправда с тех пор, как `REVIEW_LLM_REQUIRED=1` стал дефолтом.

## Предложение

1. **Одно состояние «verifier недоступен»** — `markVerifierUnavailable` в `pipeline.mjs`.
   Входы: исключение первого вызова (`error`), ни одного валидного вердикта при кандидатах
   уровня блока (`empty`), тайм-бюджет перед стадией или между батчами (`time_budget`),
   сбой хвостового батча (`batch_error`). Кап `MAX × BATCHES` — не сбой, остаётся overflow.
2. **Находка без вердикта из-за сбоя не блокер**: severity → minor, `verifierStatus: unavailable`,
   `verifierReason` хранит исходную severity. Блокером её не сделает ни гейт, ни Δ-блок.
3. **Судьбу прогона решает `REVIEW_LLM_REQUIRED`** — тот же рычаг, что для аутеджа моделей
   ревью: `1` (дефолт) — exit 1, `degraded: true`, sticky «⛔ ревью не завершено» с баннером
   «Merge заблокирован: verifier недоступен (причина) — N не проверены, перезапустите»;
   `0` — exit 0 с баннером «⚠️ Verifier недоступен … merge не блокируется».
4. **Не трогаем**: `REVIEW_VERIFIER_STRICT=0` (потребитель сам выбрал доверять агрегатору —
   прежнее поведение), `REVIEW_VERIFIER=0`, prescan-блокеры (от verifier не зависят), сбой
   при отсутствии кандидатов уровня блока (гейту нечего ждать).
5. **Инкрементальный перенос** (`REVIEW_INCREMENTAL`): файл с находкой `unavailable` или
   `overflow` не получает хэш в state, сама находка не переносится. Перенос считает находку
   прошедшей verifier (`markCarried`), и без этого «перезапустите ревью» перенёс бы
   непроверенный critical как minor — без LLM и без verifier, merge прошёл бы.
6. Наблюдаемость: событие `verifier_unavailable {reason, unverified}`, поле
   `verifierUnavailable` в событии `gate`; `verdict.blocked` и `blocked` в истории прогонов
   учитывают degraded-блок. Вход `buildSummary` — новое поле `verifierUnavailable`
   (JS и Rust, parity-кейсы `verifier unavailable *`).

## Миграция

Потребитель с дефолтами увидит: сбой verifier'а теперь блокирует merge и при пустом ответе
модели (раньше пропускал), но с честной причиной вместо «подтверждённого» блокера.
Откат — `REVIEW_LLM_REQUIRED=0` (fail-open с заметкой) или `REVIEW_VERIFIER_STRICT=0`
(прежнее поведение целиком). Формат футера и экспорта не меняется.

## Риски и что не делаем

- Нестабильный провайдер verifier'а будет чаще давать degraded-блоки. Это тот же компромисс,
  что принят для `REVIEW_LLM_REQUIRED`; сигнал — `verifier_unavailable` в JSONL.
- Не переключаемся на запасную модель как судью: блокирующий вердикт более слабой модели —
  отдельное решение (RFC 13).
- Не резервируем время под verifier в тайм-бюджете — отдельная задача; пока тайм-бюджет
  честно даёт `time_budget`.

## Оценка

Одна задача: `markVerifierUnavailable` и проводка в `pipeline.mjs`, баннер в `lib/report.mjs`
и `rust/src/report.rs`, тесты по каждому пути сбоя (падают на прежнем коде) и на неизменные
пути, parity-кейсы.
