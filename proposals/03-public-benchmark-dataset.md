# 03 — Публичный бенчмарк: датасет из чужих репозиториев, разметка по SZZ и скоринг по локации

> Категория: 🔵 Архитектура · Риск: средний · Зависимости: нет (гейт не затрагивается)

## Контекст

B6 — единственный открытый P0 в [backlog.md](../docs/backlog.md): «публичный замер
precision/recall на чужих репозиториях». Инфраструктура скоринга есть, замера нет, и весь
gold-набор — 8 кейсов из собственной практики (PR Orakul). Из-за этого утверждение
«precision выше конкурентов» опирается на выборку, которую мы сами разметили по своему же
коду: это не доказательство, а самоотчёт.

RFC фиксирует три решения, которые дороже отката: **откуда берётся разметка**, **где живут
чужие диффы** и **чем меряется recall**. Первое и третье определяют, можно ли верить цифре;
второе — то, что нельзя переиграть после того, как в git лёг гигабайт чужого кода.

## Текущее состояние

Сверено по `main` (6918b64), не по памяти.

- **Раннер и скорер не соединены.** [`bin/pr-review-gold.mjs:70-86`](../bin/pr-review-gold.mjs)
  печатает результат и выходит; JSONL никуда не пишется. При этом
  [`bin/pr-review-benchmark.mjs:50-51`](../bin/pr-review-benchmark.mjs) умеет считать сводку
  **только** из JSONL/JSON-файла прогона. То есть основной вход benchmark-CLI сегодня может
  сформировать лишь человек вручную. Это не «доработка» — это разрыв в середине пайплайна
  замера.
- **Каталог набора уже параметризуем.** И раннер (`pr-review-gold.mjs:14-16`), и скорер
  (`pr-review-benchmark.mjs:12-14`) читают `REVIEW_GOLD_DIR` с fallback на `../gold`.
  Второй набор кейсов не требует правок в обоих CLI.
- **Кейс = каталог с `meta.json` + `diff.patch`.** `runCase` (`pr-review-gold.mjs:26-35`)
  жёстко берёт `join(dir, 'diff.patch')` и гоняет пайплайн в `--dry-run`.
- **Recall меряется подстрокой в заголовке.** `titleMatches`
  ([`lib/benchmark.mjs:7-11`](../lib/benchmark.mjs)) — `normTitle(f.title).includes(needle)`.
  Других способов засчитать попадание нет: `expect` знает только `wouldBlock`,
  `mustFindTitles`, `mustNotFindTitles`.
- **Находка несёт локацию.** В футер sticky и в Δ-блок уходит
  `{ file, line, severity, title, model, fp }` ([`lib/report.mjs:443-453`](../lib/report.mjs)),
  то есть `file`/`line` — уже существующий контракт, а не новое поле.
- **Набор — 8 каталогов в `gold/`**, все со `source.pr` из Orakul; чужих репозиториев нет.

Замер добычи пар (проведён на живом GitHub API, 2026-09-03): по фразам
`regression introduced in` / `bug introduced in` / `broken by PR` в `grafana/grafana`
просмотрено 187 смерженных PR → **25 пар «фикс → PR-виновник»**, прошедших фильтр
«дифф виновника ≤ 800 строк и ≤ 15 файлов, дифф фикса ≤ 150 строк, есть общий файл».
Метод рабочий, дефекты локализованы (медиана диффа виновника — десятки строк).

## Предложение

### 1. Разметку выводим механически, а не собственным суждением (SZZ-lite)

Ground truth берётся из решения самого проекта, а не из нашего мнения о чужом коде:

1. ищем смерженный PR-**фикс**, тело которого ссылается на PR-**виновника**
   (`regression introduced in #N`, `broken by #N`, ссылка на `/pull/N`);
2. виновник даёт `diff.patch` кейса (пин по `merge_commit_sha`);
3. **локация дефекта** = файлы и строки, которые поменял фикс **и** которые есть в диффе
   виновника (пересечение). Это и есть то место, которое ревью обязано было поймать.

Кейс типа `tp` попадает в набор, только если пересечение непусто. Backport-PR
(`[release-x.y.z] …`) схлопываются по номеру виновника — иначе один дефект даёт пять
«независимых» кейсов и раздувает recall.

`clean`-контроль: смерженные PR из тех же репозиториев, на которые за ≥ 6 месяцев не
сослался ни один фикс. `expect.wouldBlock: false`.

> **Поправка после первого замера (2026-09-03).** Исходная формулировка — «любой блокер
> здесь ложный по построению» — **неверна, и это была самая опасная ошибка RFC**. Ручной
> разбор всех 7 блокирующих находок на трёх заблокированных clean-контролях не нашёл ни
> одной ложной: движок указывал на реально присутствующий в диффе код (удалённый guard
> `if f.size > 0`, `PRIMARY KEY` на MD5-хэше содержимого, проверка `closeOnOutsideClick`
> в обработчике Escape). Отсутствие ссылающегося фикса означает лишь, что дефект **никто
> не заметил**, а не что его нет.
>
> Поэтому: `clean`-контроль сам по себе меряет **не precision, а долю произвольных
> смерженных PR, на которых гейт поднимает блок**. Precision получается только после
> ручного разбора находок, и разбор обязан публиковаться вместе с цифрой. Кейс, где разбор
> подтвердил дефект, переводится в `tp` с новой локацией — иначе набор учит движок молчать
> там, где он прав.

### 2. Чужие диффы не вендорятся: `meta.json` + пин, дифф — в gitignored кэш

Новый каталог `gold-public/<id>/meta.json`, **без** `diff.patch`. Пин живёт в мете:

```json
{
  "id": "grafana-100762-influx-nested-vars",
  "type": "tp",
  "source": {
    "repo": "grafana/grafana",
    "pr": 100762,
    "sha": "<merge_commit_sha виновника>",
    "fixPr": 104067,
    "evidence": ["фикс #104067 «InfluxDB: Fix nested variable interpolation» ссылается на #100762"]
  },
  "expect": {
    "wouldBlock": true,
    "mustFindLocations": [{ "file": "public/app/plugins/datasource/influxdb/datasource.ts", "lines": [212, 219] }]
  }
}
```

Дифф тянется по пину в `.ai-review/gold-public/<id>.patch` (каталог уже gitignored).
Причины именно такого решения:

- **лицензии.** Grafana — AGPL-3.0, Discourse — GPLv2, Sentry — FSL/BSL, cal.com — AGPL.
  Втаскивать их код в наш `UNLICENSED` пакет ради теста — обязательство, которое мы не
  хотим нести и которое потом не отыграть простым `git rm` (история остаётся);
- **вес.** 20+ диффов чужих монорепо — постоянный груз в каждом клоне пакета;
- **воспроизводимость не страдает**: пин по `merge_commit_sha` даёт ровно тот же дифф, а
  `sha` в мете проверяем — если GitHub отдал другой, раннер обязан упасть, а не «примерно
  совпасть». Явного «взять свежее» в контракте нет — так же, как в structure MCP.

Новая переменная: `REVIEW_GOLD_CACHE` (по умолчанию `.ai-review/gold-public`), в
`docs/configuration.md`.

### 3. Recall — по локации, а не по подстроке в заголовке

`titleMatches` меряет совпадение слов, а находки движка формулируются по-русски, тогда как
чужой фикс описан по-английски. Для собственного набора это работало (разметку писали под
свои же формулировки); на публичном наборе подстрочная сверка померяет язык, а не recall.

Добавляем в `expect` поле `mustFindLocations: [{ file, lines: [from, to] }]` и в
`lib/benchmark.mjs` — `locationMatches(findings, target, tolerance)`: попадание засчитано,
если есть находка с тем же `file` и `line` внутри `[from - tolerance, to + tolerance]`.
`tolerance` — 3 строки (тот же допуск, что у carry-over по позиции), задаётся в мете
кейса, дефолт в коде.

Существующие `mustFindTitles` остаются и работают как раньше: старые кейсы не трогаются,
`mustFindLocations` — аддитивное поле. В `aggregateBenchmark` заводится **отдельный**
счётчик `locationRecall` рядом с существующим `recall` (титульным): смешивать «нашёл нужное
слово» и «попал в нужную строку» в одну цифру нельзя, а перегружать `recall.targets` двумя
разными величинами — значит потерять возможность их разделить.

> **Поправка после первого замера.** Заголовочная величина — не доля локаций, а
> **доля кейсов, где найдена хотя бы одна размеченная строка** (`locationCaseRecall`).
> Счёт по локациям наказывает дважды за один дефект, размазанный по нескольким строкам:
> в `sentry-78722` один и тот же продублированный guard-блок дал две локации, движок указал
> на первую и получил 1/2, хотя класс дефекта нашёл. Счёт по локациям сохраняется рядом как
> более строгая величина, но заголовком не является.
>
> **Допуск ±3 строки остаётся необоснованным.** Он перенесён из carry-over по отпечатку, где
> решает другую задачу («та же находка между прогонами»). Здесь вопрос иной — «указал ли
> рецензент на дефект», и правильной единицей, вероятно, является ханк или символ, а не
> окно в строках. Пока величина не пересмотрена, любой отчёт обязан печатать использованный
> допуск рядом с цифрой.

### 4. Соединить раннер со скорером: `pr-review-gold --jsonl <файл>`

`pr-review-gold` дописывает по строке на кейс в формате, который уже читает
`scoreFromRecord` (`{ id, meta, findings, wouldBlock, code }`). Это закрывает разрыв из
«Текущего состояния» и делает связку `gold → benchmark` воспроизводимой одной командой.

### 5. Добыча кейсов — скриптом в пакете, а не разово руками

`bin/pr-review-gold-harvest.mjs <repo…>`: ищет пары, применяет фильтры, печатает
кандидатов и по `--emit <dir>` раскладывает заготовки `meta.json` с уже посчитанным
пересечением строк. Разметка остаётся проверяемой: в `source.evidence` пишется ссылка на
фикс, по которой любой может пересчитать вывод.

Отбор кейсов в набор — ручной шаг поверх скрипта: скрипт не решает, что дефект
«поймаемый по диффу», он лишь готовит кандидатов.

> **Поправка после первого замера.** Публиковать одно число отбракованных недостаточно:
> проверить чужой отбор по числу нельзя. Список отбракованных с критерием лежит в
> `gold-public/rejected.json` машиночитаемо и обновляется вместе с набором.

### 6. Конфигурация прогона — часть протокола, а не деталь исполнения

Цифра замера без указания профиля не интерпретируется: движок спроектирован работать с
профилем репозитория, и «31% без профиля» и «31% с профилем» — разные утверждения. Поэтому:

- набор гоняется под **зафиксированным в пакете** профилем `profiles/public-benchmark.json`
  (подключён в `npm run benchmark:public` через `REVIEW_PROFILE`);
- отчёт обязан печатать профиль, модели ролей и допуск локаций рядом с цифрами;
- **текст промпта в профиле — часть измеряемой конфигурации.** Правки в нём, сделанные
  после того, как цифры увидены, — это подгонка. Менять его допустимо только вместе с
  повторным замером и явной отметкой, что база сменилась.

### 7. Один прогон на кейс — не оценка

`grafana-61729` в двух прогонах дал разный вердикт гейта при одной и той же находке.
Заявления о precision требуют нескольких прогонов и публикации разброса; пока их нет,
отчёт обязан говорить, что цифра снята одним прогоном.

### 8. Замер не герметичен

Отказ от вендоринга (§ 2) имеет цену, которую исходный RFC не назвал: диффы тянутся по
сети, и сеть становится участником измерения — два кейса первого прогона умерли на
`fetch failed` посреди часового прогона. `--validate` теперь прогревает кэш заранее, но
свойство остаётся: воспроизводимость держится на пине, а не на локальности.

## Миграция

Ломающих изменений нет: `gold/` и `npm run check` не затронуты.

1. `lib/benchmark.mjs` — `locationMatches`, поддержка `expect.mustFindLocations`, отдельная
   строка в отчёте (юнит-тесты на пустой/промах/попадание/границу допуска).
2. `bin/pr-review-gold.mjs` — `--jsonl`, `--gold-dir` уже через env.
3. `bin/pr-review-gold-harvest.mjs` + `lib/gold-fetch.mjs` (пин, кэш, проверка `sha`).
4. `gold-public/` — кейсы (цель первой итерации: 8 `tp` + 4 `clean` из ≥ 3 репозиториев).
5. `docs/benchmark.md` — раздел про публичный набор; отчёт замера —
   `docs/benchmark-public.md` с датой, моделями и стоимостью прогона.

Публичный набор **не входит** в `npm run check`: он требует сети и LLM. Отдельная команда
`npm run benchmark:public`.

## Риски и что не делаем

- **Разметка неполна по построению.** SZZ-пара доказывает, что дефект был, но не что он
  единственный. Поэтому набор меряет **recall по известным дефектам**, а не абсолютный
  recall, и в отчёте это должно быть написано прямо. Заявлять «recall N%» без этой оговорки
  нельзя.
- **Смещение выборки.** Мы берём дефекты, которые проект заметил и описал ссылкой на
  виновника, — то есть заметные и признанные. Тихие дефекты в выборку не попадают.
- **Не все дефекты видны из диффа.** Часть регрессий требует контекста всего репозитория;
  такие кейсы отбраковываются на ручном шаге, и число отбракованных публикуется — иначе
  отбор превращается в подгонку.
- **Сравнения с конкурентами в этом RFC нет.** Мы меряем себя на воспроизводимом наборе.
  Цифра CodeRabbit/Greptile на том же наборе — отдельная работа с их прогоном, и без него
  формулировка «точнее, чем X» не появляется.
- **Не делаем:** не вендорим чужой код; не трогаем merge-гейт и `EXPORT_VERSION`; не
  переводим существующие кейсы `gold/` на локации; не вводим семантическую близость на
  эмбеддингах (локация объективнее и не требует модели).
