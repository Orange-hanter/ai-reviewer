# 02 — Точная привязка покрытия функций: FNL/FNA, сверка FNH, детектор противоречий

> Категория: 🟡 Адаптация · Риск: низкий · Зависимости: нет

## Контекст

PR #12 закрыл ложное «покрыто»: `FNDA` адресует функцию только по имени, и при повторе
имени непокрытая функция получала чужие хиты. Сейчас счётчик привязывается по порядку
записей — istanbul пишет `FN` и `FNDA`, обходя один и тот же `fnMap`
([istanbul-reports/lib/lcovonly](https://github.com/istanbuljs/istanbuljs)), поэтому N-я
`FNDA` относится к N-й одноимённой `FN`.

Это работает, но держится **на поведении писателя, а не на ключе формата** — потому
привязка и помечена `attribution: 'order'` с уверенностью не выше `extracted`. RFC описывает,
как перейти от «мы знаем, как пишет istanbul» к «формат сам это говорит», и что делать, пока
такого ключа во входе нет.

## Текущее состояние

Сверено по `main` и по реальному отчёту (`restate-api`, 339 файлов), не по памяти:

- [`lib/structure-lcov.mjs`](../lib/structure-lcov.mjs) даёт три ветки привязки:
  `attribution: 'name'` (имя уникально), `'order'` (имя повторяется, число `FN` совпало с
  числом `FNDA`), `'unresolved'` (числа разошлись → `hits: null`, `status: unresolved`);
- **парсер игнорирует `FNF`/`FNH`/`LF`/`LH`/`BRF`/`BRH`** — итоговые счётчики, которые писатель
  кладёт в тот же файл;
- замер на реальном отчёте: вычисленные `found`/`hit` совпали с объявленными `FNF`/`FNH`
  **во всех 339 файлах из 339**, предупреждений парсера — ноль;
- одноимённые функции нашлись ровно в одном файле, и там формат ровно такой, на который
  рассчитана привязка по порядку:

  ```
  SF:src/independent-agent/dto/submit-kyc.dto.ts
  FN:101,type
  FN:107,type
  FNF:2
  FNH:0
  FNDA:0,type
  FNDA:0,type
  ```

  Наш разбор: `type@101: hits=0 (order)`, `type@107: hits=0 (order)`, итог `hit=0` — совпадает
  с объявленным `FNH:0`;
- `lcov` 2.5 доступен в Homebrew. Прежняя причина отложить `FNL`/`FNA` — «ни бинаря, ни
  примера отчёта на машине» — **снята**.

## Предложение

Три шага по возрастанию цены. Каждый самостоятелен, порядок — порядок отдачи на вложенный час.

### Шаг 1. Сверка с объявленными `FNF`/`FNH` (дёшево, ничего не додумывает)

Писатель уже сообщает, сколько функций он насчитал и сколько из них исполнялось. Это
независимая проверка нашей привязки, доступная без единого допущения о формате.

- парсить `FNF`/`FNH` в запись файла;
- если наши `functions.found`/`functions.hit` расходятся с объявленными — писать
  предупреждение и понижать уверенность observation'ов этого файла;
- расхождение не является поводом подменять наши числа объявленными: `FNH` — сводка, она не
  говорит, *какая именно* функция исполнялась.

Измеренная цена ложных срабатываний: **ноль на 339 файлах**. Функции с `hits: null`
(`unresolved`) в сравнении не участвуют — иначе честное «неизвестно» само порождало бы
расхождение.

### Шаг 2. `FNL`/`FNA` из LCOV 2.x — привязка по индексу, а не по имени

В LCOV 2.x есть записи, где функция адресуется индексом, а не именем. Это снимает
неоднозначность в принципе и даёт право на `attribution: 'index'` с уверенностью `exact`.

**Порядок работ важен, потому что формат нельзя реализовывать по памяти:**

1. прочитать писателя как источник истины — `lcovutil.pm` / `geninfo` в
   [linux-test-project/lcov](https://github.com/linux-test-project/lcov), тем же приёмом,
   которым мы подтвердили порядок записей у istanbul;
2. `brew install lcov` и сгенерировать образец на C-файле с двумя одноимёнными `static`
   функциями — то есть на входе, который заведомо создаёт неоднозначность;
3. заморозить образец в `fixtures/` как контрактные данные;
4. только после этого реализовать разбор.

Приоритет источников при разборе: `FNL`/`FNA` → `order` → `name` → `unresolved`. Появление
индексных записей ничего не ломает: они дополняют, а не заменяют `FN`/`FNDA`.

Если шаг 1 к этому моменту сделан, у нас есть и проверка: на образце с `FNL`/`FNA` результат
обязан сойтись с `FNH`.

### Шаг 3. Детектор противоречий по `DA` — сигнал, а не способ привязки

Ранее я отклонил сверку с `DA` строки объявления, и **как способ привязки отклоняю по-прежнему**:
для поднятых объявлений (`function foo() {}`) счётчик строки не означает исполнения тела, а у
функций-выражений считает присваивание. Выводить из `DA` число хитов — значит сочинять.

Но у `DA` есть корректное одностороннее применение: **противоречие**. Если функции приписаны
`hits > 0`, а `DA` её строки объявления равен нулю, внутри одного файла сошлись два
несовместимых утверждения. Это повод усомниться в привязке — и только:

- срабатывает **только на понижение**: предупреждение и снижение уверенности, никогда не
  повышение заявки и никогда не смена `covered` → `uncovered`;
- применяется только там, где `DA` для этой строки вообще есть;
- ровно тот случай, где ошибка была бы видна: в исходном дефекте `handler@50` имел
  `hits=7` при `DA:50,0`.

Это самый слабый из трёх сигналов и самый шумный кандидат, поэтому он третий: включать
после того, как шаг 1 покажет, что расхождения вообще случаются.

## Миграция

Всё аддитивно. `attribution` получает новое значение `'index'`; `'name'`, `'order'` и
`'unresolved'` сохраняются. Потребителю (cod-doc) читать по-прежнему `status` и `confidence` —
поле `attribution` диагностическое. Схема `structure-assessment.v1` не меняется: `exact`,
`extracted`, `ambiguous` и `unresolved` в ней уже есть.

## Риски и что не делаем

- **Не реализуем формат по памяти.** Шаг 2 начинается с чтения писателя и заморозки образца;
  без них задача не берётся в работу — иначе получим уверенность `exact`, опирающуюся на
  догадку, что ровно тот дефект, который чинил PR #12.
- **Не используем `DA` как источник привязки** — только как детектор противоречий.
- **Не подменяем наши числа объявленными `FNF`/`FNH`**: сводка не говорит, какая именно
  функция исполнялась.
- **Не трогаем merge-гейт**: structure-контур в нём не участвует (см.
  [RFC 01](01-structure-platform-boundary.md)).
- Не поддерживаем прочие диалекты покрытия (Cobertura, JaCoCo) — вне рамок этого RFC.

## Оценка

Три задачи, каждая с регрессионным тестом:

| Шаг | Объём |
|-----|-------|
| 1. Сверка `FNF`/`FNH` | полдня; данные уже в файле, ложных срабатываний на реальном отчёте нет |
| 2. `FNL`/`FNA` | день, из них половина — чтение писателя и заморозка образца |
| 3. Детектор `DA` | полдня, после того как шаг 1 покажет частоту расхождений |
