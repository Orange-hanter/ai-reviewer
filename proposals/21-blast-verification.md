# 21 — Проверка blast-находок: verifier решает, ломает ли изменение вызывающий код

> Категория: 🟡 Адаптация · Риск: средний · Зависимости: [RFC 16](16-blast-required.md) (граф обязателен), [RFC 17](17-gate-holes.md) (решение — свойство находки), [RFC 18](18-verifier-unavailable.md) (сбой verifier'а), [RFC 20](20-rust-primary.md) (новое поведение — только в Rust)

## Контекст

Blast-radius находит код **вне PR**, который зависит от изменённого символа, и выдаёт
находку «код вне PR зависит от `S` — проверьте совместимость». По замыслу (CLAUDE.md,
«Два независимых судьи») такая находка — soft: она блокирует merge только после вердикта
verifier'а `verified`.

Разбор 2026-10-20 показал, что в режиме `moa`, который ставит шаблон
`examples/ci/pr-review.yml`, правило не исполняется ни разу: strict-refutation понижает
blast-находку до `minor` ещё до того, как она доходит до verifier'а. Прогон через
публичный API:

```
after refutation: minor downgraded_no_claims
verifier blockers: 0
```

Вторая проблема становится видна, как только снята первая: verifier не получает файл
вызывающего кода, а его промпт подталкивает подтвердить blast-находку её же собственным
доказательством. Этот RFC описывает, как проверка должна работать целиком, а не только
как снять понижение.

## Предложение

### Что доказывает blast-находка

Blast-находка — **гипотеза**, а не дефект: «вызывающий код `C:L` вне PR может сломаться
из-за изменения символа `S`». Блокировать merge она вправе, только когда verifier докажет
три факта:

1. **Контракт `S` изменился** — в диффе видно изменение сигнатуры, возвращаемого значения,
   выбрасываемых ошибок или поведения, на которое опирается вызов.
2. **Вызов несовместим с новым контрактом** — в показанной строке `C:L` видно, как вызов
   нарушает новый контракт (число/порядок/тип аргументов, ожидание прежнего результата).
3. **Вызов не обновлён в PR** — `C` нет среди изменённых файлов (это blast гарантирует при
   эмиссии), и PR не делает изменение `S` обратно совместимым (перегрузка, значение по
   умолчанию).

Граф доказывает только существование ребра `C → S`; факты 1–2 доказывает verifier по коду.

### Поток

| # | Стадия | Как должно быть |
|---|--------|-----------------|
| 1 | Эмиссия | Без изменений: `major`, `source: 'blast-radius'`, confidence по ребру. |
| 2 | Refutation | Blast-находка **пропускается**, как prescan: refutation измеряет согласие advisors, а у детерминированной находки advisors нет — понижать её за отсутствие голосов значит путать «никто не возразил» с «никто не спрашивал». `refutationStatus: 'not_applicable'`, счётчик `stats.skippedBlast`. |
| 3 | Отбор verifier'а | Blast-major — обычный кандидат в блокеры. Внутри одного уровня severity LLM-находки идут раньше blast-находок: при капе `REVIEW_VERIFIER_MAX` предположение графа не вытесняет находку, которую уже согласовало жюри. Находка, не поместившаяся в кап, идёт по RFC 17/18, как и остальные. |
| 4 | Контекст verifier'а | Для blast-кандидата прикладывается окно ±`REVIEW_BLAST_VERIFY_MARGIN` (дефолт 20) вокруг `C:L` из рабочего дерева — файл вне PR, поэтому читается отдельно от `contentMap`, через `deps`, с тем же отказом от symlink наружу, что и `readChangedFiles`. Добавляется хунк диффа, где меняется `S` (он уже есть в `annotated`). Если файл прочитать не удалось, кандидат остаётся без доказательства: `verifierStatus: 'unverified'`, `minor`, блокировки нет. |
| 5 | Промпт verifier'а | Отдельное правило для кандидатов с `source: blast-radius` (ниже). `VERIFIER_BLAST_RULE` остаётся для LLM-находок, которые ссылаются на blast как на улику; на blast-кандидатов оно не распространяется. |
| 6 | Гейт | Без изменений: блокирует только `verified` + уровень в `blockOn` + `confidence ≥ REVIEW_CONFIDENCE_MIN`. Сбой verifier'а — по RFC 18 (`unavailable`, судьбу решает `REVIEW_LLM_REQUIRED`). |
| 7 | Инкремент | Без изменений: не переносится, считается заново. |

Поведение одинаково в `moa` и `consensus`: режим LLM-стадий не должен решать,
проверяется ли детерминированная находка.

### Правило verifier'а для blast-кандидата

Текст (английский, как остальные системные промпты; `reason` — по-русски):

- **verified** — только если по показанному коду видны оба факта: в диффе изменён контракт
  `S`, и строка `C:L` использует `S` так, что нарушает новый контракт. В `reason` — обе
  строки: где изменился контракт и где вызов его нарушает.
- **rejected** — контракт `S` не изменился (правка тела без смены поведения для
  вызывающего), изменение обратно совместимо или строка `C:L` совместима с новым
  контрактом.
- **downgrade** (→ `minor`) — контракт изменился, но несовместимость по показанному коду
  не доказать (вызов через обёртку, динамический аргумент). Это замечание для человека,
  а не блок.
- Существование ребра в blast-radius **не является** доказательством: оно уже учтено
  самим фактом кандидата.

### Контракты

- Rust `apply_refutation(…)`: условие пропуска — `prescan || source == BLAST_FINDING_SOURCE`.
- Rust `select_verifier_candidates(…)`: ключ сортировки — `(sev_order, is_blast)`.
- `buildVerifierFileContents(contentMap, candidates, { margin, readOutside })` — новый
  параметр `readOutside(path) → entry|null` для кандидатов вне `contentMap`; в пайплайне
  передаётся из `deps`.
- Rust `prompt.rs`: `VERIFIER_BLAST_CANDIDATE_RULE`, включается, только если среди
  кандидатов есть blast-находка (тот же приём, что условный `VERIFIER_BLAST_RULE`).
- Env: `REVIEW_BLAST_VERIFY` (`0` | `shadow` | `1`) и `REVIEW_BLAST_VERIFY_MARGIN`
  — в `lib/config.mjs`, `rust/src/config.rs`, `docs/configuration.md`.
- Observability: в событии `refutation` — `skippedBlast`; в событии verifier — разбивка
  вердиктов по `source`.

### Тесты

- Rust unit: blast-major проходит refutation с прежней severity; `select` берёт blast
  после LLM-находки того же уровня.
- `test/pr-review.pipeline.test.mjs`: `moa` + blast-major + verifier `verified` → exit 1;
  `rejected` → находка снята, exit 0; нет вердикта → `minor`, exit 0; файл caller'а не
  читается → `unverified`, exit 0; режим `shadow` → exit 0 и событие `blast_would_block`.
- Eval fixture `gate-blast-verified-blocks-moa` (счётчик seed-кейсов 20 → 21).
- Parity: refutation и отбор расходятся с deprecated JS-копией намеренно — кейсы
  помечаются rust-owned (RFC 20), JS не правится.

## Миграция

Это изменение впервые разрешает blast-находкам блокировать merge в `moa` — у потребителя
появляются новые блокировки. Включение — тем же путём, что у судьи гейта (RFC 13):
`0` → `shadow` → дефолт.

1. **`REVIEW_BLAST_VERIFY=shadow`** — шаги 2–5 работают, вердикты пишутся в артефакт и
   observability, но гейт blast-находку не блокирует: пишется событие `blast_would_block`
   с файлом, строкой и `reason` verifier'а.
2. **Замер:** gold с blast-кейсами и shadow-прогоны потребителя. Порог переключения
   дефолта: на собранной выборке нет ни одного `blast_would_block`, который человек при
   разборе счёл ложным. Без размеченных blast-кейсов в gold дефолт не переключается.
3. **`REVIEW_BLAST_VERIFY=1`** по умолчанию; строка в CHANGELOG «для потребителя» и откат
   `REVIEW_BLAST_VERIFY=0` (возврат к нынешнему поведению: в `moa` blast не блокирует).

Формат футера sticky, `EXPORT_VERSION` и контракты `swarm`/`structure` не меняются; новые
поля verifier-статистики в экспорте — аддитивные, по правилу `EXPORT_VERSION` растёт.

## Риски и что не делаем

**Риски**

- **Ложные блоки**: verifier подтверждает несовместимость, которой на самом деле нет.
  Защита: правило требует обе строки в `reason`, shadow-этап до дефолта, откат флагом.
- **Вытеснение из капа verifier'а.** Большой PR с общим символом даёт десятки
  blast-находок. Защита: blast идёт после LLM-находок того же уровня; попавшие сверх
  капы уходят в `overflow` по RFC 17 и не блокируют.
- **Цена.** Окна файлов вне PR увеличивают вход единственного вызова verifier'а. Окно
  ±20 строк и только для blast-кандидатов, попавших в кап; размер входа уже пишется в
  `prompt_chars` — до переключения дефолта его стоит проверить на gold.
- **Чтение вне PR.** Файл caller'а берётся из рабочего дерева чекаута PR — того же,
  откуда уже читаются изменённые файлы; секреты в него не попадают. Symlink наружу
  отклоняется так же, как в `readChangedFiles`.

**Не делаем**

- Blast-находка не блокирует без verifier'а ни в каком режиме — soft-правило гейта
  остаётся.
- Confidence по ребру не повышается после `verified`: при пороге 0.8 блокировать
  по-прежнему могут только рёбра EXTRACTED. Поднимать ли INFERRED-ребро, подтверждённое
  показом строки вызова, — решение по итогам shadow-замера, отдельной правкой.
- Новых ролей и LLM-вызовов не добавляем: проверка идёт в существующем batch-вызове
  verifier'а.
- Перенос blast-находок инкрементальным прогоном не вводим.
- JS-копии refutation и отбора не правим (RFC 20).

## Оценка

| # | Задача | Объём |
|---|--------|-------|
| 1 | Rust: пропуск blast в refutation, порядок в отборе, флаг `REVIEW_BLAST_VERIFY` в конфиге (JS + Rust), parity rust-owned | малый |
| 2 | Контекст verifier'а: окно файла caller'а через `deps`, `unverified` при нечитаемом файле | средний |
| 3 | Промпт: `VERIFIER_BLAST_CANDIDATE_RULE`, условное включение, тест на текст | малый |
| 4 | Shadow: событие `blast_would_block`, разбивка вердиктов по `source`, тесты пайплайна, eval fixture | средний |
| 5 | Gold-кейсы с blast-caller'ами и замер; решение о дефолте | средний |

Задачи 1–4 мержатся вместе за флагом с дефолтом `0`; задача 5 — условие переключения дефолта.

## Вызовы через namespace-импорт (BLV-009)

**Проблема.** Graphify (graphifyy 0.9.87) не связывает вызов `m.S()` при `import * as m from './A'`
(или `const m = require('./A')`) с функцией `S` в JS/TS: у `getTgToken` и `startTelegram` в
Orakul нет зависимого `app/server.js`, хотя он вызывает обе. Есть только файловое ребро
`server.js —imports_from→ telegram.js`. В Python (`from pkg import mod as m` → `m.f(`) граф
такие вызовы связывает — поломка cod-doc поймана именно через него.

**Частота** (HEAD интеграционных веток, файлы кода без тестов): Orakul — 6 файлов из 806,
128 вызовов `m.f(`, среди них точки входа `server.ts`, `platform-server.ts`; Restate и Gateway —
0. Класс узкий, но приходится на файлы, которые связывают модули целиком.

**Решение — фолбэк в движке** (`lib/graphify.mjs`, не upstream: Graphify мы не контролируем):
1. для изменённого символа `S` с узлом в файле PR `A` (`.js/.mjs/.cjs/.ts/.tsx/.jsx`) взять из
   графа файлы, импортирующие `A` (входящие рёбра `imports`/`imports_from` файлового узла), кроме
   файлов PR;
2. в каждом найти namespace-алиас `A` — `import * as m from '<путь к A>'` или
   `const m = require('<путь к A>')`, путь разрешается относительно импортёра с перебором
   расширений и `index`;
3. строки `m.S(` — зависимости `relation: calls`.

Confidence таких рёбер — `EXTRACTED`: и импорт, и вызов прочитаны из кода буквально, это не
догадка. Иначе (INFERRED, 0.75) подтверждённая verifier'ом находка не прошла бы порог
`REVIEW_CONFIDENCE_MIN` = 0.8, и фолбэк ловил бы, но не блокировал. Слой/кластер — как у прочих
зависимостей (обогащение по узлу файла); чтение — `deps.readFile`, лимит — 50 импортёров на
символ. Python не трогаем: граф там справляется.

**Проверка** (2026-10-22, gold Orakul: blast-кейс и 5 clean, остальные проекты фолбэк не
затрагивает). Blast-кейс `getTgToken` **пойман**: зависимость `app/server.js:90
[calls][EXTRACTED] cross-community`, verifier — verified («getTgToken стал async, server.js:90
вызывает без await — Promise всегда truthy»), `blast_would_block` на `:90`. Попутно фолбэк
нашёл `startTelegram` → `:90` и `register` → `:77` — verifier отклонил оба (контракт не менялся).
Итог по настоящим поломкам — **2 из 2**.

**Ложные блоки — не от фолбэка, но найдены этим прогоном.** Clean-кейс `orakul-968d83e1`:
PR переименовал `IngredientPicker.jsx` → `.tsx`, импортёры вне PR остались с `'./IngredientPicker.jsx'`;
verifier подтвердил «путь больше не существует» — 3 `blast_would_block`. Ложно: на этом коммите
`vite.config.js` держит резолвер `jsToTsResolver`, подменяющий `.jsx` → `.tsx`; конфиг сборки
verifier'у не показан. Это рёбра `imports` графа, а не namespace-вызовы; в предыдущем замере те
же кандидаты получили rejected — вердикт по этому классу нестабилен. Условие «ноль ложных
блоков» для дефолта больше не выполнено — BLV-010.

## Контракт — в месте использования (BLV-010)

**Проблема.** Clean-кейс `orakul-968d83e1`: PR переименовал `IngredientPicker.jsx` → `.tsx`,
импортёры вне PR остались с `'./IngredientPicker.jsx'`, Vite-резолвер `jsToTsResolver` это
покрывал. Компонент используется как JSX (`<IngredientPicker …/>`, `PrepsManager.jsx:303`), вызова
`IngredientPicker(` нет — перенос на вызов не сработал, находка осталась на строке импорта `:3`, и
verifier судил путь импорта («файла больше нет») вместо контракта. Вердикт по таким кандидатам
нестабилен: в одном прогоне rejected, в другом verified.

**Решение** — два слоя:
1. **Детерминированно** (`pipeline.mjs`, при чтении файла вызывающего кода): место использования
   символа — вызов `S(` / `m.S(` или JSX-тег `<S` (`findCallLines`). Находка переносится на
   ближайшее. Нет ни одного — символ в файле только импортирован (или передан без вызова):
   несовместимость контракта функции на импорте не проявляется, находка → `minor`,
   `verifierStatus: unverified`, verifier её не получает (и не платит за неё).
2. **Промпт** (`VERIFIER_BLAST_CANDIDATE_RULE`, Rust): разрешение спецификатора импорта
   (расширение, алиас, `index`, path mapping) решает конфиг сборки, которого verifier не видит;
   переименованный или перенесённый файл — не доказательство поломки. Судить только строку
   использования.

Оба истинных блока замеров — на вызовах (`update_status(`, `getTgToken()`), правило 1 их не
задевает. Цена — находки о символе, переданном без вызова (`arr.map(S)`), блокировать не будут;
для blast-класса это редкость, и они остаются в отчёте как minor.

**Проверка** (2026-10-22, gold shadow): clean-кейс `orakul-968d83e1` три прогона подряд —
`blast_would_block` 0 в каждом. Находки по компонентам перенесены на JSX
(`PrepsManager.jsx:303`, `FinanceTab.jsx:278`, `MenuTab.jsx:1028`), verifier судит контракт и
отклоняет все три во всех прогонах («props products, excludeIds, onAdd, onClose сохранены»); ещё 4
находки на прогон — только импорт, minor без verifier'а. Оба blast-кейса по-прежнему пойманы:
cod-doc `tasks_status.py:52`, Orakul `server.js:90` — verified, `blast_would_block`.

## Символ — затронутый, тип — по аннотации (BLV-011)

**Проблема.** Orakul PR #660 (`v0.7.0`): PR добавил необязательный параметр в
`export type OnUpdate` (`app/client/src/types.ts:213`). В отчёте шесть blast-находок
«Код вне PR зависит от … — проверьте совместимость»: `OnUpdate`, `OnCreate`, `ShowToast` в
`CategoriesCenter.tsx` и `DishSalesModal.tsx`. Ни одну verifier не видел. Причины две:

1. **Символы, которых PR не трогал.** `collectBlastSymbols` добирает экспорты из полного
   текста изменённого файла — все, до `REVIEW_MAX_SYMBOLS`. Добор нужен, чтобы правка тела
   функции без строки `export` давала символ; но `types.ts` экспортирует десятки типов, и в
   blast ушли `OnCreate`, `ShowToast` — текст находки «`OnCreate` затронут изменениями» ложен.
2. **Тип не вызывается.** `findCallLines` ищет `S(` и `<S`. Тип используется аннотацией
   (`onUpdate: OnUpdate;`) — использования «нет», находка уходит в `minor` / `unverified`
   без verifier'а (BLV-010) и остаётся в отчёте как непроверенная гипотеза.

**Решение.**

1. **Добор — только охватывающее объявление** (Rust, `collect_blast_symbols`). Для каждой
   изменённой строки файла (добавленной; для удаления — строки перед ним) берётся ближайшее
   объявление-экспорт не ниже её: правка внутри `OnUpdate` даёт `OnUpdate`, а не все экспорты
   файла. Строки изменений считаются из того же диффа (`diff` во входе операции); без `diff`
   поведение прежнее — так зовёт ревью-MCP. Изменённая строка до первого объявления (импорты)
   символа не даёт. Нерегрессия: правка тела `makeDataStore` по-прежнему даёт `makeDataStore`.
2. **Аннотация типа — использование** (`findCallLines`): для имени с заглавной кроме `<S`
   учитываются `: S`, `as S`, `extends S`, `implements S`, `satisfies S`; строки `import` /
   `export … from` — нет (BLV-010: на импорте контракт не проявляется). Находка переносится на
   строку аннотации и идёт к verifier'у, который судит контракт по диффу и окну вокруг неё.

**Цена.** П. 1 сужает вход Graphify: файл, где изменён не-экспортированный хелпер между
экспортами, отнесётся к экспорту выше — это шире точного, но уже «все экспорты файла».
Экспорт через `export { a }` в конце файла, чьё объявление выше без `export`, по правке тела
`a` не находится — такой символ ловит только строка `export { … }` в самом диффе.
