# 05 — Инкрементальный прогон: не ревьюить заново то, что не менялось

> Категория: 🔵 Архитектура · Риск: средний · Зависимости: [RFC 04](04-token-economy.md)

## Контекст

PR ревьюится по многу раз: каждый push прогоняет **весь** дифф целиком, хотя между прогонами
изменились два файла из тридцати. В журнале `.ai-review/observability` PR #6 прогонялся три
раза, и каждый стоил полную цену — 12 чанков, 48 вызовов, ~1.3M токенов.

Побочный эффект тот же по природе: стабильность набора находок между прогонами одного PR —
`0.08–0.2`. Модели заново формулируют то же самое другими словами. Перепрогон неизменившегося
файла не только стоит денег, но и вносит шум в Δ-блок, который должен показывать реальные
изменения, а не дисперсию генерации.

## Текущее состояние

Сверено по коду, не по памяти:

- [`pipeline.mjs`](../pipeline.mjs) строит чанки по **всему** `annotated` на каждом прогоне;
  `readChangedFiles` читает все изменённые файлы;
- carry-over уже есть, но у него другая роль: `readPriorStickyData` достаёт находки прошлого
  прогона из футера sticky и отдаёт их в промпт как «уже поднятое» (`priorFindings`), чтобы
  модель не переформулировала. В набор находок текущего прогона они **не попадают**;
- [`lib/findings.mjs`](../lib/findings.mjs) `filterStalePriorFindings` снимает prior-находку,
  если отпечаток кода под ней (`findingFingerprint`) исчез из файла;
- футер sticky хранит находку урезанной: `file`, `line`, `severity`, `title`, `model`, `fp` —
  без `body`, `confidence`, `advisorClaims`, `verifierStatus`;
- `applyRefutation(..., { strict: true })` понижает `critical`/`major` **без `advisorClaims`**
  до `minor`; `runVerifierStage` проверяет кандидатов в блокеры отдельной моделью.

## Предложение

### Единица сравнения — вход модели, а не коммит

Для каждого файла считается `sha256(секция диффа + приложенный контекст)`. Совпал хэш —
модель увидела бы ровно то же самое, значит вызов можно не делать.

Почему не SHA коммитов и не GitHub compare: перебазирование меняет SHA, не меняя входа, и
наоборот — смена `REVIEW_MAX_FILE_LINES` меняет вход при том же коммите. Плюс сравнение по
входу не требует похода в API и одинаково работает локально и в CI.

Оба слагаемых обязательны: только дифф — и правка соседней функции в том же файле (она
приезжает контекстом) осталась бы незамеченной; только контекст — и не заметили бы смену hunks.

### Что происходит с находками по неизменившимся файлам

Они **переносятся в набор текущего прогона** как полноценные — со своими `body`,
`confidence`, `severity` и вердиктами жюри и verifier — и помечаются `carriedOver: true`.

**Перенос выполняется ПОСЛЕ refutation и verifier, а не до.** Это главное решение RFC.
Обе стадии находка уже прошла в том прогоне, где была найдена, и принесла свои вердикты с
собой. Пропусти её через них ещё раз — и `strict`-refutation понизила бы подтверждённый
блокер до `minor` только потому, что в ЭТОМ прогоне жюри по нему не высказывалось: файл не
менялся и никому не показывался. Гейт при этом молча ослабевал бы с каждым push.

Находка по **изменившемуся** файлу не переносится никогда: её место в коде могло уехать, и
решать это должен свежий прогон, а не сравнение хэшей.

### Где живёт состояние

Свой файл — `paths.incrementalState` (`.ai-review/incremental/state.json`): версия, номер PR,
`headSha`, отпечаток конфигурации, хэши входа по файлам, находки.

Почему не футер sticky: он ограничен размером комментария GitHub и хранит находки урезанными.
Перенести через него блокер, не расширив формат, нельзя, а формат футера — контракт с
потребителем (смена ломает Δ-блок и harvest 👍/👎).

Почему не артефакт экспорта: он версионирован и читается снаружи; складывать в него служебное
состояние прогона значит смешивать назначения.

Цена решения: в CI состояние надо сохранять между прогонами (`actions/cache` на
`.ai-review/incremental/`). Нет кэша — каждый прогон полный, то есть ровно сегодняшнее
поведение. Деградация безопасная.

### Когда прогон принудительно полный

- нет состояния, оно другой версии или от другого PR;
- **изменился отпечаток конфигурации**: модели, роли, режим слияния, раскладка промпта,
  нарезка чанков, параметры гейта, порог маршрута/допуска verifier, таймаут LLM.
  Прошлые находки получены другим движком и сопоставлять их с новыми нельзя;
- изменились все файлы PR;
- каждый `REVIEW_INCREMENTAL_FULL_EVERY`-й прогон (default 10) — страховка от накопления
  дрейфа: находка, перенесённая двадцать раз подряд, ни разу не проверялась заново.

### Отчёт

Sticky получает строку «♻️ Инкрементальный прогон: N из M файлов не изменились…». Без неё
читатель не может отличить «advisors ничего не нашли» от «advisors этот файл не видели».

## Миграция

`REVIEW_INCREMENTAL` по умолчанию **выключен**: экономия здесь достаётся ценой того, что часть
отчёта собрана не этим прогоном, и включать это должен оператор осознанно. Включение и
выключение обратимы, состояние самоинвалидируется по отпечатку конфигурации.

## Риски и что не делаем

- **Риск:** дефект появляется во взаимодействии изменённого файла с неизменённым (правка
  сигнатуры в `foo.ts` ломает вызов в `bar.ts`). Инкрементальный прогон `bar.ts` заново не
  ревьюит. Смягчение: `bar.ts` остаётся в карте PR и в blast-radius, а blast-radius-находки
  детерминированы и пересчитываются каждый прогон. Полностью риск снимает только полный
  прогон — отсюда `FULL_EVERY` и выключенный дефолт.
- **Риск:** состояние протухло относительно кода (кто-то правил файлы мимо PR).
  Смягчение: хэш считается по входу текущего прогона, а не по записанному — расхождение
  означает «изменилось», то есть переревью.
- **Не делаем:** не расширяем футер sticky (контракт с потребителем), не трогаем
  `resolveBlockers`, `applyRefutation` и verifier — перенос устроен так, чтобы обойтись без
  правки их семантики.
- **Не делаем:** не пытаемся переносить prescan- и blast-находки: они детерминированы, дёшевы
  и пересчитываются каждый прогон.

## Оценка

| | |
|---|---|
| Задач | 1 (модуль + подключение + тесты) |
| Эффект | повторный прогон PR, где изменился 1 файл из 30: LLM-вызовы только по нему; если не изменилось ничего — **ноль вызовов** |
| Гейт решения | тест «перенесённый блокер по-прежнему блокирует merge» и «находка по изменённому файлу не переносится» |
