# 13 — Судья гейта

> Категория: 🔵 Архитектура · Риск: средний · Зависимости: [RFC 04](04-token-economy.md) (цена стадии), [RFC 05](05-incremental-review.md) (перенос находок), [RFC 06](06-actionability-single-penalty.md) (скоринг), `docs/review-quality.md` §2.6

Черновик. Декомпозиция уже есть — план `gate-judge` в cod-doc, задачи GATE-001…025. Сверка
этих задач с кодом нашла допущения, без исправления которых коридор либо пуст, либо проверяет
не ту находку. Они вынесены в «Вопросы владельцу» и «Поправки к декомпозиции»; пока они не
закрыты, чек-лист «Готов к декомпозиции» не проставлен.

## Контекст

Merge сейчас блокируется фактом находки: есть кластер с `consensusBlock` — exit 1. Отсюда
два дефекта, которые план `gate-judge` берётся лечить.

1. **Гейт не умеет уставать.** История прогонов доезжает до рендера, но не до решения;
   номера круга нет, возраста находки нет. Единственный исторический сигнал в решении —
   булев `repeated` (+2 к actionability).
2. **minor/nit не влияют ни на что.** К minor ведут три машины понижения (strict-refutation,
   strict-verifier, overflow капа), и понижение до minor — тихое снятие с гейта. При этом
   ярлык severity нестабилен: одна тема на трёх прогонах одного sha получала critical, major
   и minor (комментарий в `lib/actionability.mjs`, цитируется в `docs/review-quality.md` §2.6).

Предложение — стадия «судья гейта»: один вызов модели после детерминированного гейта,
который видит весь набор находок и историю кругов и может перевернуть вердикт внутри коридора.

## Текущее состояние

Сверено по коду на `1a4b204`:

- **Блокеры.** `resolveBlockersJs` ([`lib/findings.mjs:355-360`](../lib/findings.mjs)):
  кластеры с хотя бы одним `consensusBlock`, блокер кластера — `g.find((f) => f.consensusBlock) || g[0]`.
  `clusterFindings` ставит флаг **всем** членам кластера (`lib/findings.mjs:552-558`), включая
  minor/nit. Итог — `blockers.length` → exit 1 (`pipeline.mjs:918`).
- **Отчёт и exit code расходятся.** Sticky считает `blockerClusters` через `g[0]?.consensusBlock`
  (`pipeline.mjs:813`), `applyPrescanBlockPolicyJs` гасит флаг выборочно (`lib/findings.mjs:640-650`),
  а prescan-находки идут в `allFindings` первыми (`pipeline.mjs:649-652`). Смешанный кластер
  «advisory-prescan + LLM-major» даёт exit 1, а sticky — заголовок «💬 есть замечания» с
  ✅-строками (`lib/report.mjs:534, 547-551`). Rust уже на
  some-семантике (`rust/src/findings.rs:576-585`). `verdict.blocked` и `verdictReproducibility`
  считаются от того же `blockerClusters` (`lib/report.mjs:533, 594`).
- **Verifier по умолчанию делает почти все блокеры подтверждёнными.** `REVIEW_VERIFIER` и
  `REVIEW_VERIFIER_STRICT` включены по умолчанию (`lib/config.mjs:209, 332`) и в шаблоне CI
  (`examples/ci/pr-review.yml:164-166`). В strict major/critical без вердикта → minor
  (`lib/verifier.mjs:106-114`), сверх капа 12 → minor (`pipeline.mjs:213-222`). Блокер без
  `verified` остаётся только в случаях: prescan с `prescanBlock`; verifier пропущен по дедлайну
  или упал (`pipeline.mjs:143-147, 232-236`); `REVIEW_VERIFIER_STRICT=0`; перенесённая находка
  (`REVIEW_INCREMENTAL`, `pipeline.mjs:801-803`) без вердикта из своего прогона; представитель
  кластера — minor рядом с `verified` major.
- **Скор доказуемости до маршрута.** `actionabilityScore` пишется в находку в
  `findingsFmt.classify` (`pipeline.mjs:830`). Раньше он есть, только если `runVerifierStage`
  отобрал advisory-кандидатов через `routeFindings` (`pipeline.mjs:161-169`) — нужен verifier,
  `verifyAdvisory > 0` и неистёкший дедлайн. Причины скора лежат текстом (`actionabilityReasons`),
  обратное отображение в ключи — `REASON_KEY_BY_WHY` (`pipeline.mjs:48-50`). Скоры из стадии
  verifier посчитаны **до** его вердикта и не содержат +3 за `verified`.
- **История в футере.** Запись — `footerData` с окном `runs` из 5 (`lib/report.mjs:676-682`),
  slim-находка `{file,line,severity,title,model,dupCount?,fp?}` (`lib/report.mjs:575-582`),
  без ограничения числа. Чтение режет находки до 40 и окно до 5 на обеих ветках
  (`lib/github.mjs:137-138, 463-467`) и возвращает только `{findings, runs, sha}`. Обе ветки
  разбирают футер в JS: Rust даёт только HTTP-транспорт, разбора футера в `rust/src/github.rs` нет.
- **Воспроизводимость.** `verdictReproducibilityJs` (`lib/report.mjs:456-463`) по прогонам
  одного sha из окна футера: `{ total, blocked, flaky }`, null при < 2 прогонах. Замер
  #533 — блок в 4 из 6 прогонов при неизменном диффе.
- **Цена вызова.** Ключ цены — опция `callType` в `chatJson` (`lib/llm.mjs:200`, по умолчанию
  `'review_json'`), а не поле события `llm_call`. Verifier её не передаёт и учитывается как
  `review_json/<model>`. `chatJson` повторяет вызов на пустом/обрезанном выходе
  (`lib/llm.mjs:212-218`).
- **Профильные вставки промпта.** Ровно четыре ключа — advisor/specialist/aggregator/verifier —
  и в JS (`lib/profile.mjs:165-172`), и в Rust (`rust/src/config.rs:499-504`); неизвестные
  отбрасываются.
- **Eval.** `applyVerifierVerdicts` вызывается без `strictUnverified`, шага overflow нет
  (`lib/eval.mjs:69-74`) — strict-режим eval не воспроизводит.
- **Слово `judge`** в коде как идентификатор не встречается.

## Предложение

### Решения, зафиксированные владельцем (перенесены дословно из GATE-001)

- **Полномочия — коридор:** `resolveBlockers` остаётся детерминированным полом; судья
  переворачивает вердикт в обе стороны внутри двух рельсов.
- **Круг ≥ 5 — решает судья:** отдельного правила затухания нет, номер круга и возраст
  находки — факты в досье.
- **minor/nit — доказуемость + накопление:** поднять можно только уже доказуемую находку либо
  файл с кворумом minor.
- **Воспроизводимость — один вызов, temperature 0;** расхождения ловит существующий
  `verdictReproducibility` по sha.
- **Рельс 1 сильнее номера круга:** сколько бы кругов ни прошло, «твёрдый» блокер
  (`prescan && prescanBlock` или `verifierStatus === 'verified'`) судья снять не может.

### Устройство

Модули и сигнатуры — как в задачах плана:

- `lib/history.mjs` (только JS): `nextRunIndex(priorFooter)`, `annotateFindingAge(findings, priorFindings)`;
  ключ сопоставления — `point` из `findingKeysJs`, второго ключа не заводим.
- Футер: скаляр `runIndex` (без окна), у slim-находки `seen` и `firstSeenSha` (7 символов,
  `seen` опускается при 1). Аддитивно, старый футер читается с дефолтами.
- `lib/gate-judge.mjs`: `buildJudgeDossier`, `classifyHardBlockers`, `minorQuorumFiles`,
  `promotionEligible`, `applyJudgeVerdict`, `createJudgeRunner`. Досье без кода: поля
  находок, история, детерминированный вердикт, пороги; кап 60, блокеры всегда в срезе.
- Вердикт модели: `{ decision, reason, release[], promote[], confidence }`. Рельсы проверяет код:
  release твёрдого → отказ в `railViolations`; promote неподходящего → отказ; битый JSON →
  детерминированный исход; `pass` без поимённого release при мягком блокере → `blanketPass`.
- Стадия `runJudgeStage` после `attachFingerprints` и расчёта блокеров, до маршрута; fail-open;
  не бежит без LLM (`ok.length === 0`); результат в обе точки выхода (dry-run и боевая).
- Находки не удаляются: `judgeReleased` / `judgePromoted` + `judgeReason` меняют вес в гейте,
  не видимость. `judgePromoted` читают двое — маршрут inline и auto-triage, как `actionabilityScore`.
- Конфиг: `REVIEW_JUDGE` (0), `REVIEW_JUDGE_MODEL`, `REVIEW_JUDGE_TEMPERATURE` (0),
  `REVIEW_JUDGE_PROMOTE_MIN` (= `REVIEW_ACTIONABILITY_MIN`), `REVIEW_JUDGE_MINOR_QUORUM` (5),
  `REVIEW_JUDGE_MAX_FINDINGS` (60); JS и Rust-конфиг.
- Наблюдаемость: события `judge` / `judge_skip` / `judge_error`, в `verdict` — раздельно
  `deterministicWouldBlock` и `finalWouldBlock`. Экспорт: блок `judge`, `seen`/`runIndex`, рост
  `EXPORT_VERSION`.

### Поправки к декомпозиции (по сверке с кодом)

Уточнения, без которых задачи сделают не то, что задумано. Их нужно внести в задачи до
checkout.

1. **Твёрдость — по кластеру, а не по представителю (GATE-009, GATE-010).** Блокер — первый
   член кластера с флагом, и флаг есть у всех членов. `classifyHardBlockers` обязан считать
   кластер твёрдым, если твёрд хоть один его член; release применяется к кластеру целиком.
   Иначе судья «отпускает» minor-представителя, а подтверждённый major в том же кластере
   молча уходит вместе с ним.
2. **Скор до судьи (GATE-008, GATE-009, GATE-014).** Судья должен видеть `actionabilityScore`
   у всех находок, но сейчас скор появляется в `classify`, после точки вставки. Разделить
   `classify` на «скоринг» (до судьи) и «маршрут» (после): находка по-прежнему несёт один скор
   с одного расчёта, а поднятая успевает в inline. Без этого при выключенном verifier рельс 2
   открыт только prescan и кворуму.
3. **Возраст за пределом 40 находок (GATE-004, GATE-006).** Чтение футера режет находки до
   40 в порядке «prescan → LLM → перенесённые»; всё после 40-й теряет `seen` и сбрасывается в 1
   — именно у крупных PR, где усталость и нужна. Поднять кап чтения (запись и так без капа;
   65 000 символов режут `md`, а не футер, `lib/report.mjs:686-687`) или писать футер в порядке
   убывания значимости.
4. **`runIndex` на чтении (GATE-004, GATE-005).** Обе ветки `lib/github.mjs` возвращают только
   `{findings, runs, sha}` — расширить возврат. Rust-зеркала чтения футера нет и не нужно:
   паритет — кейс в `github.parity.mjs` на старый и новый футер.
5. **Ключ цены (GATE-013, GATE-019).** Судья вызывает `chatJson(..., { temperature, callType: 'judge' })`,
   иначе его цена сольётся с `review_json`. «Один вызов» может стать двумя из-за ретрая
   `chatJson` — считать это в оценке цены.
6. **`judgeExtra` (GATE-012).** Промпт не зеркалится, но ключ профиля — да: без правки
   `rust/src/config.rs:499-504` вставка молча теряется на машине с бинарём.
7. **Гвард `ok.length` (GATE-014, GATE-015f).** Fail-closed ветка бежит только при
   `!ok.length && (llmRequired || !allFindings.length)` (`pipeline.mjs:656`); при
   `REVIEW_LLM_REQUIRED=0` и prescan-находках прогон идёт обычным путём. Гвард судьи нужен в
   обоих случаях, кейс (f) — на оба пути.
8. **Маршрут поднятой находки (GATE-016).** `judgePromoted` должен перебивать не только порог
   и `REVIEW_STRICT`, но и `s.inlineable`, иначе находка на строке вне диффа всё равно уйдёт в свод.
9. **auto-triage (GATE-017).** `buildTriageContext` должен получать блокеры **после** судьи
   (`pipeline.mjs:900`), иначе поднятый minor попадает в `advisoryOnly`.
10. **Eval и strict (GATE-022).** Eval не воспроизводит strict-verifier; фикстура
    `judge-release-soft` проверяет конфигурацию, которой в CI по умолчанию нет. Либо научить
    eval strict-режиму, либо явно пометить фикстуру как non-strict.
11. **Итог судьи — во все производные (GATE-014, GATE-018, GATE-020).** Кроме `blockers`, от
    вердикта зависят `blockerClusters` в `buildSummary` (`pipeline.mjs:838`) и payload события
    `verdict`, который собирается в `lib/report.mjs:705-709` (и `rust/src/report.rs`). Без этого
    sticky, `verdict.blocked` и `verdictReproducibility` покажут детерминированный исход при
    изменённом exit code — тот же класс расхождения, что чинит GATE-002.
12. **Съехавшие ссылки** в описаниях задач (около двадцати) — поправить при grooming;
    основные: `classify` на `:830`, событие `verdict` на `:853`, «Verifier (Pass B)» в
    `docs/configuration.md` на `:126-135`, «Два независимых судьи» в `docs/architecture.md` на
    `:137-142`, счётчик eval ещё и в `docs/architecture.md:188`.

### Вопросы владельцу

**В1. Что судья отпускает при конфигурации по умолчанию.** Рельс 1 + strict-verifier (дефолт
движка и шаблона CI) делают почти каждый блокер твёрдым: мягкий блокер остаётся только при
сбое или пропуске verifier, при `REVIEW_VERIFIER_STRICT=0` и у перенесённых находок. Значит,
в штатном прогоне судья **только ужесточает** гейт (promote), а дефект 1 — «гейт не умеет
уставать» — не лечится: подтверждённый блокер на пятом круге по-прежнему не снимается.
Варианты:

| Вариант | Что даёт | Цена |
|---|---|---|
| а. Принять | Судья = подъём minor + разбор сбоев verifier; дефект 1 вычеркнуть из цели RFC | Честная цель, стадия дешевле; усталость остаётся нерешённой |
| б. Ослабить рельс 1 для `verified` с `seen ≥ N` | Лечит дефект 1 | Отменяет зафиксированное «рельс 1 сильнее номера круга»; verified — тоже вердикт модели |
| в. Усталость — детерминированно, вне судьи | Правило по `seen`/`runIndex` для **неподтверждённых** классов; судья — только promote | Отменяет «круг ≥ 5 — решает судья»; зато проверяемо в eval |

Рекомендация — (а): решение владельца о рельсе 1 обосновано (verified — независимая модель
вне пула), а цель RFC должна совпадать с тем, что коридор физически может сделать.

**В2. Теневой режим до включения.** Судья на метаданных без кода — это политика над полями,
которые код уже знает; его вклад — только в чтении `title`/`body` (дубли, «major» про стиль).
Доказать, что он лучше правила, одним живым прогоном (GATE-024) нельзя. Предложение:
`REVIEW_JUDGE=shadow` — вызов и события пишутся, вердикт не применяется; дефолт (GATE-025)
решать по N прогонам в тени с ручной разметкой «согласен ли человек», а не по одному.

**В3. Кворум minor.** Кворум 5 на файл допускает подъём minor с нулевым скором. Семейства FP
(`docs/false-positives.md`) кучкуются по файлу, и шумный файл становится поводом блокировать.
Считать в кворум только minor со скором ≥ 1 или от ≥ 2 разных моделей?

## Миграция

- `REVIEW_JUDGE=0` в движке — поведение бит-в-бит прежнее; при В2 — промежуточный `shadow`.
- Футер и экспорт расширяются аддитивно; `EXPORT_VERSION` растёт. Смена дефолта на `1` —
  breaking для потребителя (решение гейта меняется при том же коде), отдельная строка в
  CHANGELOG и согласованный пин.
- GATE-002 (some-семантика `blockerClusters`) — независимый `fix:`, делается первым и без RFC.

## Риски и что не делаем

- **Недетерминизм гейта.** temperature 0 у Ollama Cloud не гарантирует одинакового выхода;
  плюс ретрай `chatJson`. Меряем `deterministicWouldBlock` против `finalWouldBlock` в `verdict`.
- **Prompt injection** через текст находок (они цитируют код PR). Автору PR выгоден release, а
  release ограничен рельсом 1; promote автору невыгоден. Промпт объявляет находки данными, но
  защита — рельсы в коде, не промпт.
- **Третий судья размывает «два независимых судьи».** Коридор не трогает детерминированный пол;
  при В1-а судья его только ужесточает.
- **Не делаем:** судья не создаёт находок (только переоценивает по id); не трогает structure;
  не заменяет verifier и не входит в пул advisors; не меняет маршрут сам по себе — только
  через `judgePromoted`; промпт судьи не зеркалится в Rust.

## Оценка

План `gate-judge`: 25 задач в шести секциях (A — RFC; B — история; C — коридор; D — стадия;
E — читатели и вывод; F — конфиг, eval, доки, живой прогон, дефолт). Поправки выше меняют
объём B (кап чтения футера) и C/D (разделение `classify`); при В2 добавляется режим `shadow`
в GATE-014/021 и серия теневых прогонов в GATE-024.

Критерий успеха — не зелёные тесты, а цифры в журнале: доля прогонов, где судья изменил
вердикт; согласие человека с `reason`; `flaky` по `verdictReproducibility` до и после; цена
стадии относительно прогона.
