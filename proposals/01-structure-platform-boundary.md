# 01 — Граница structure-платформы: часть пакета merge-гейта или соседний пакет

> Категория: 🔵 Архитектура · Риск: средний · Зависимости: нет

## Контекст

PR [#6](https://github.com/Orange-hanter/ai-reviewer/pull/6) принёс structure-платформу
(смержен в `main` 2026-09-03):
versioned facts/assessment/obligations, EvidenceReceipt, провайдеры Graphify/SCIP/LCOV,
mutation/property evidence и MCP-сервер с пином по SHA. Итогом 39 файлов и +6527 строк:
2835 из них — код в `lib/structure*.mjs` (≈29% строк `lib/`), остальное схемы, тесты,
fixtures и документация.

Вопрос RFC — **не качество кода**, а граница: должен ли пакет, который потребитель пинит и
запускает в своём merge-гейте, нести ещё и off-PR аналитику структуры.

**RFC написан после мержа — и это ровно тот случай, ради которого заводится процесс.**
Схемы и имена бинарей уже в `main`, то есть контракт опубликован раньше, чем обсуждён.
Поэтому документ решает две задачи: зафиксировать границу пост-фактум (пока за неё не
зацепился код) и задать порог, при котором следующий такой контур проходит через RFC до
реализации, а не после.

Бэклог уже требует такой процесс (пункт A5) и уже содержит прецедент правила «абстракция —
только под реального второго потребителя» (пункт D18 про мультифордж). RFC применяет то же
правило к обратной ситуации — не к абстракции, а к разрастанию.

## Текущее состояние

Сверено по `main` после мержа (не по описанию PR):

- **Гейт не зависит от structure.** Ни один модуль движка не импортирует `lib/structure*.mjs`;
  `pipeline.mjs` в диффе не изменён вообще. Прогон ревью не становится тяжелее.
- **Structure почти не зависит от движка**: из общего кода тянутся только `lib/util.mjs`
  (4 импорта) и `lib/config.mjs` (1, из бинаря). Остальное — внутренние
  `structure-*` модули.
- **Но общий конфиг уже знает про structure**: `lib/config.mjs` +37/−3 строк, включая
  `DEFAULT_STRUCTURE_TRUST_TIER` и `REVIEW_STRUCTURE_*` внутри `loadReviewConfig()` —
  того самого замороженного объекта, который описывает прогон гейта.
- **Публичная поверхность выросла**: `package.json` — 2 новых бинаря
  (`pr-review-structure`, `pr-review-structure-mcp`) и каталог `schemas/` в `files`;
  `index.mjs` — 39 строк новых экспортов.
- **Качество прогона не пострадало**: на `main` после мержа `npm test` — 314 тестов
  зелёные (48 из них structure), `npm run eval` — fixtures стабильны, внешних зависимостей
  не добавлено (бейдж «зависимостей 0» остаётся верным). Замерено, не взято из описания PR.
- **Код по существу не ревьюился**: 6527 строк за один заход. Настоящий ревью — отдельная
  работа, этот RFC её не заменяет.

## Предложение

Принять вариант **«оставить в репозитории за явной границей»** и зафиксировать саму границу
правилами, а не намерением.

Часть пунктов уже нельзя «принять до кода» — они становятся follow-up задачами в `main`.
Отвергнутые альтернативы:

| Вариант | Почему нет |
|---------|-----------|
| Соседний пакет сразу | Второго потребителя пока нет; общий код (`util.mjs`, receipts) пришлось бы дублировать или заводить третий пакет. Тот же довод, что в D18 |
| Оставить как смержено, без правил | Граница держится только на дисциплине: первый же импорт `structure-*` из `pipeline.mjs` растворит её без единого падающего теста |

Что фиксируем:

1. **Контрактный тест «гейт не знает про structure»**: ни один файл из `pipeline.mjs`,
   `bin/pr-review.mjs` и `lib/*.mjs` (кроме `lib/structure*.mjs`) не импортирует
   `structure-*`. Правило проверяемое — сейчас оно верно, но ничем не удержано.
2. **Конфиг structure — отдельным загрузчиком** (`loadStructureConfig(env)` в
   `lib/structure.mjs`), а не полями внутри `loadReviewConfig()`. `REVIEW_STRUCTURE_*`
   не должны попадать в замороженный объект прогона гейта: этот объект описывает, как
   блокируется merge.
3. **Своя версия протокола** — `STRUCTURE_PROTOCOL_VERSION` независим от `EXPORT_VERSION`
   (в PR уже так; фиксируем как правило, чтобы схемы не начали ездить вместе с артефактом
   ревью).
4. **Критерий выделения в отдельный пакет** — любое из: появился второй потребитель
   протокола помимо cod-doc; structure требует внешней зависимости (ломает «0 зависимостей»);
   доля structure в репозитории продолжает расти после первого реального использования.
5. **MCP-сервер описан как поверхность**: `pr-review-structure-mcp` — процесс, который
   агент запускает и которому отдаёт пути. Пин по SHA и confinement путей в PR есть;
   в `docs/structure.md` нужен явный абзац «что сервер читает и чего не делает».

## Миграция

Ничего не ломается: гейт не менялся, потребители запускают тот же `bin/pr-review.mjs`.
Стоимость для потребителя — размер чекаута по пину (в CI это `actions/checkout` всего репо).

Все пять пунктов — follow-up задачи поверх `main`, потому что #6 уже смержен. Пункт 2
(вынос конфига) — единственный, который меняет уже опубликованную поверхность: делать его
надо до того, как `REVIEW_STRUCTURE_*` начнут читать из `loadReviewConfig()` снаружи.

## Риски и что не делаем

- **Риск размывания идентичности.** README продаёт один тезис: доказательный merge-гейт.
  Второй крупный контур в том же пакете делает ответ на «что это» длиннее — это цена,
  которую принимаем сознательно и пересматриваем по критерию (4).
- **Риск ревью-долга.** 6527 строк без построчного ревью — отдельная задача, а не
  побочный эффект этого RFC. Тесты (48 structure-кейсов) показывают, что контур собран,
  но не заменяют ревью границ доверия и парсеров внешних форматов.
- **Не делаем**: не выносим structure в отдельный репозиторий сейчас; не подключаем
  structure к merge-гейту (никаких блокировок по structure-находкам); не переносим
  snapshot-хранилище и obligations из cod-doc в этот пакет.

## Оценка

4 задачи: контрактный тест границы; вынос конфига в `loadStructureConfig`; абзац про MCP
в `docs/structure.md`; отдельный ревью-проход по коду PR #6. Первые три — день, четвёртая
зависит от глубины ревью.
