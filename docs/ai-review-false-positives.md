# AI-ревью: лог ложных срабатываний (накопление аналитики)

Назначение: копить наблюдения о **ложных** консенсус-блокерах авто-ревью
(`@orakul/ai-reviewer`, workflow «AI code review»), чтобы улучшить пайплайн и **seed eval fixtures** (см. [architecture.md](architecture.md)).
Пишем сюда, когда AI-ревью блокирует merge корректного PR (Tests+build = pass,
typecheck/lint/unit/e2e зелёные), а находка при проверке оказывается неверной.

Формат записи: дата · PR · паттерн · доказательство ложности · что сделали.
Append-only — новые записи снизу. R8 может дописывать краткие блоки в конец (`REVIEW_FEEDBACK_MD_APPEND=1`); основной контекст — **ручные** записи ниже.

### Как связать запись с eval fixture

1. Оформить запись в §Журнал (паттерн, PR, доказательство).
2. На PR: 👎 на inline или label `ai-review-fp`.
3. Harvest → candidate → [fixtures/README.md](../fixtures/README.md).
4. Ссылка на fixture id в строке «что сделали».

## Наблюдаемые паттерны (сводка)

1. **«Файл/тест не в диффе» при том, что он в диффе.**
   Модель комментирует строки файла (т.е. видит его), но в выводе пишет «в PR нет
   изменений в `<file>`» и блокирует. Проверяется `gh pr diff <N> --name-only` —
   файл там есть. Чистая галлюцинация, не чанкование.

2. **Конвергенция накапливает устаревшие находки.**
   Бот подгружает «прошлые находки (сходимость)» и переутверждает их, не сверяясь
   с уже внесённым фиксом. От прогона к прогону число консенсус-кластеров может
   **расти** (наблюдали 1 → 3 → 3 → 4), т.е. цикл расходится, а не сходится.
   «Запушить фикс и перепрогнать» делает хуже.

3. **Фиксы, разнесённые по коммитам, «теряются».**
   Если замечание раскрыто в одном коммите, а фикс — в следующем, ревьюер
   (инкрементальный дифф + перенос находок) их не коррелирует и повторяет находку.
   Схлопывание ветки в один коммит помогает не всегда (см. PR #254).

4. **Гипотеза несуществующей серверной логики.**
   Модель предполагает наличие server-side кода (напр. серверный `prepBalance`),
   которого по дизайну нет (расчёт только на клиенте), и требует «обновить сервер».

5. **Чанкование разрывает связь «код ↔ его тест».**
   Ревьюер чанка с UI-кодом не видит чанк со спекой и пишет «нет e2e», хотя спека
   в PR есть (классика PR #245).

## Рекомендации пайплайну (черновик)

> Перенесено в [25-ai-code-review-pipeline-spec.md §7–§8](25-ai-code-review-pipeline-spec.md) как as-built + roadmap. Ниже — исторический черновик до eval harness.

- Перед постингом находки «нет реализации/теста/файла X» — проверять X по списку
  изменённых файлов PR; если X там есть, находку гасить (или понижать до non-block).
- Не переутверждать перенесённую находку без проверки, что соответствующие строки
  в текущем диффе НЕ изменились.
- Подмешивать в контекст каждого чанка связанные `*.spec.ts`/`*.test.ts` и полный
  список изменённых файлов (анти-галлюцинация «не в диффе»).
- Стоп-кран расхождения: если число консенсус-кластеров между прогонами растёт —
  это сигнал зацикливания, а не реальных проблем.
