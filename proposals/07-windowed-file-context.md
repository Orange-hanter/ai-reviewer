# 07 — Окно контекста для advisors и жюри: меньше файла, честнее промпт

> Категория: 🔵 Архитектура · Риск: средний · Зависимости: [RFC 04](04-token-economy.md) (методика замера и решение 1), [RFC 05](05-incremental-review.md) (хэш входа как единица сравнения)

## Контекст

[RFC 04](04-token-economy.md) закрыл дешёвые статьи входа: добавленные файлы контекстом не
прикладываются, чанк без кода не зовёт специалистов, роли на одной модели опрашиваются одним
вызовом. После этого прогон разложился так, что дальше резать почти нечего — и это надо
сказать прямо, прежде чем предлагать следующий шаг.

Замер на том же `pr-6.patch` (264 КБ, 35 файлов), скрипты в `/tmp`-каталоге замера, текущий
код `worktree-token-economy`:

| Статья входа | Символов | Доля |
|---|---:|---:|
| Аннотированный дифф (артефакт под ревью) | 1 107 850 | 60,8 % |
| **Контекст изменённых файлов** | **418 880** | **23,0 %** |
| Фиксированные части промптов (системные, карта PR, референсы жюри) | 296 544 | 16,3 % |
| **Всего** | **1 823 274** | ≈ 456k токенов (÷4, как `estimateTokens` в [`lib/structure-context.mjs:10`](../lib/structure-context.mjs)) |

9 чанков, 8 из них полные, 33 вызова. Дифф несжимаем: это и есть то, что ревьюят. Фиксированные
части уже прошли два прохода правок и дают десятки символов на вызов. Остаётся контекст —
**104 761 уникальных символа, оплаченных четырежды** (три советника + жюри на каждый полный
чанк), 12 693 символа на вызов.

Внутри этих 104 761 символов лежит текст, который ни одна находка прогона не процитирует: файл
на 363 строки прикладывается целиком ради одного хунка на две строки. Verifier эту задачу уже
решил — `windowFileEntry` режет файл до окон вокруг интересующих строк, — но advisors и жюри
продолжают получать файл целиком.

Мешает не техника: функция окон написана, оттестирована и работает в продакшене второго
прохода. Мешает то, что **системный промпт жюри продаёт полный файл дословно**, и любое окно
делает эту фразу ложью. Ложное обещание в промпте хуже маленького контекста: оно приглашает
модель утверждать отсутствие («эта функция больше нигде не вызывается») по усечённому виду.
Поэтому RFC меняет размер контекста и текст промпта одним решением, а не двумя.

## Текущее состояние

> Снимок кода до реализации. Окна сделаны в `412acaa` и вышли в 0.3.0: промпт больше не обещает полный файл, номера строк ниже указывают на код до правки. Итог — в разделе «Замер реализации».

Сверено по коду, не по памяти.

**Функция окон уже есть и уже используется — одним читателем.**

- [`lib/context-window.mjs:50`](../lib/context-window.mjs) `windowFileEntry(entry, lines, { margin = 80 })` —
  чистая функция: режет запись `contentMap` до окон ±`margin` вокруг строк `lines`,
  пересекающиеся и соприкасающиеся окна сливает, пропуски помечает
  `… (строки N–M пропущены)`. Возвращает запись **без изменений**, если формат не распознан
  (маркер добавленного файла), список строк пуст или окна покрывают файл целиком — то есть
  «нечего резать» не стоит ни байта накладных;
- [`lib/context-window.mjs:88`](../lib/context-window.mjs) `buildVerifierFileContents(contentMap, candidates, { margin })` —
  обёртка для Pass B; вызывается из [`pipeline.mjs:189`](../pipeline.mjs) с
  `margin: verifier.contextMargin` (`REVIEW_VERIFIER_CONTEXT_MARGIN`, default 80);
- в Rust модуль не портирован и порта не требует: это чистый JS-хелпер вне контура паритета.

**Промпт обещает полный файл — в трёх местах, и одно из них уже врёт.**

- [`lib/prompt.mjs:316`](../lib/prompt.mjs), системный промпт агрегатора (зеркало —
  [`rust/src/prompt.rs:255`](../rust/src/prompt.rs)):

  > `CONTEXT AND "NO OPEN QUESTIONS": you have the FULL content of the changed files (not only the diff) and`
  > `the blast-radius of their dependencies. USE this to RESOLVE your doubts instead of leaving them open.`

- [`lib/prompt.mjs:331`](../lib/prompt.mjs) — заголовок секции:
  `## Full content of changed files (PR version — context beyond the hunks)`
  (зеркало — [`rust/src/prompt.rs:583`](../rust/src/prompt.rs));
- [`lib/prompt.mjs:404`](../lib/prompt.mjs) — заголовок той же секции в промпте verifier'а:
  `## Full content of changed files` (зеркало — [`rust/src/prompt.rs:536`](../rust/src/prompt.rs)).

Третий случай — **уже ложное обещание в текущем коде**: с момента, когда
[`pipeline.mjs:189`](../pipeline.mjs) начал подавать в verifier окна, заголовок «Full content»
описывает вырезку. Это не аргумент «раз уже врём, соврём и дальше», а обратное: правку надо
сделать в обоих местах сразу, потому что второй проход именно на этом контексте выносит
вердикт по блокерам.

**Запрет absence-claims включается не всегда.**
[`lib/prompt.mjs:424`](../lib/prompt.mjs): `split` истинно, только когда чанку достались не все
файлы PR или файл виден не полностью (`partialPaths`). Блок `HARD RULE — NO ABSENCE CLAIMS`
([`lib/prompt.mjs:459`](../lib/prompt.mjs), зеркало
[`rust/src/prompt.rs:440`](../rust/src/prompt.rs)) печатается внутри `if (split)`
([`lib/prompt.mjs:451`](../lib/prompt.mjs)). **PR из одного чанка запрета не получает вовсе** —
сегодня это верно, потому что в одном чанке модель видит всё; с окнами это перестаёт быть
верным, и запрет обязан включаться и там.

**Прецедент разметки усечённого контекста уже есть.**
[`lib/diff.mjs:388-390`](../lib/diff.mjs): файл, чей контекст обрезан по `maxContextBytes`,
попадает в `truncated` и оттуда в `partialPaths` — карта PR метит его
`[THIS PART, SOME HUNKS ONLY]`. Метка для окон не годится: её пояснение говорит
`has further hunks shown to another part`, а у файла с окнами все хунки на месте, урезан
только контекст между ними. Переиспользовать её значит поменять одну ложь на другую.

**Кто на самом деле читает `contentMap`.** Полный перечень читателей вне сборки промпта — два:

- [`pipeline.mjs:408`](../pipeline.mjs) → [`lib/diff.mjs:326`](../lib/diff.mjs)
  `collectBlastSymbolsJs` — сканирует **полные тексты** `.ts/.js`-файлов регулярками
  `EXPORT_SYMBOL_PATTERNS` и добирает имена экспортов, которых нет в изменённых строках.
  Это единственный читатель, которому полный файл нужен по существу: `export function foo`
  стоит в начале файла, а хунк — в конце, и никакое окно вокруг хунков этот `export` не
  захватит. Обрежь контекст до окон раньше — и blast-radius молча опустеет;
- [`pipeline.mjs:453`](../pipeline.mjs) → [`lib/incremental.mjs:41`](../lib/incremental.mjs)
  `fileInputHashes(changedPaths, sections, contentMap)` — считает `sha256(секция диффа +
  приложенный контекст)`; по определению RFC 05 хэш обязан считаться по тому, **что увидела
  бы модель**.

Чего в этом списке **нет** и почему это важно:

- FP-фильтр [`lib/findings.mjs:220`](../lib/findings.mjs) `filterFalsePositiveFindings` работает
  по `${f.title} ${f.body}` и списку `changedPaths`; `requiresPath` в
  [`lib/fp-patterns.mjs:83`](../lib/fp-patterns.mjs) матчится по путям. Содержимое файлов он не
  видит вообще — окна на него не влияют;
- отпечатки [`lib/findings.mjs:272`](../lib/findings.mjs) `attachFingerprints(findings, files)`
  и инвалидация carry-over `filterStalePriorFindings` читают `files` — карту `parseDiff`
  (`rec.text`: номер строки → её текст из **диффа**), а не `contentMap`. Сходимость между
  прогонами от окон не зависит;
- prescan (eslint + ast-grep) ходит по путям в рабочем каталоге, а не по `contentMap`;
- `actionability`, `resolveBlockers`, кластеризация, экспорт — контекста файлов не касаются.

**Добавленные файлы в эту статью не входят — двойного счёта нет.** Решение 1 RFC 04 уже
работает: [`pipeline.mjs:392`](../pipeline.mjs) собирает `collectAddedPaths(diff)`, и
[`lib/diff.mjs:161`](../lib/diff.mjs) кладёт для них `addedFileMarker(path)` вместо тела. На
`pr-6.patch` это 26 из 35 файлов, и все 26 маркеров вместе весят **2 653 символа** — 2,5 % карты
контекста. `windowFileEntry` их не трогает: `splitEntry` не распознаёт запись без тела в
кавычках и возвращает её как есть ([`lib/context-window.mjs:22`](../lib/context-window.mjs)).
Вся экономия этого RFC берётся из **девяти** оставшихся файлов.

## Предложение

### 1. Центр окна для advisors — изменённые строки файла, а не находка

Verifier центрирует окно на `line` кандидата; у advisors кандидатов ещё нет — они бегут до
того, как появилась первая находка. Единственный детерминированный центр, доступный на этой
стадии, — **строки, которые PR трогает в этом файле**: `[...files.get(path).validLines]` из
[`lib/diff.mjs:250-275`](../lib/diff.mjs) (номера RIGHT-стороны для `+`-строк и контекстных
строк хунка, то есть хунк плюс три строки git-контекста с каждой стороны).

Этот центр честнее, чем кажется на первый взгляд, но и слабее: он гарантирует, что модель
видит окрестность каждой правки, и **не** гарантирует, что она видит объявление функции, тело
которой правят с 300-й строки. За это платим — см. риски.

Цена разброса измерима, и она неравномерна. Девять файлов `pr-6.patch` с реальным содержимым
(`cov` — доля файла, покрытая окнами):

| Файл | Симв. | Строк | Хунков | `+`-строк | ±80 | ±40 | cov ±80 | cov ±40 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| `lib/config.mjs` | 22 014 | 449 | 4 | 37 | 17 325 | 11 986 | 0,80 | 0,56 |
| `docs/configuration.md` | 17 378 | 279 | 1 | 26 | 12 053 | 6 884 | 0,67 | 0,38 |
| `lib/profile.mjs` | 14 734 | 363 | 1 | 2 | **5 482** | 3 388 | 0,37 | 0,23 |
| `README.md` | 13 124 | 264 | 3 | 13 | 11 468 | 8 440 | 0,84 | 0,60 |
| `docs/backlog.md` | 11 085 | 177 | 1 | 6 | 10 512 | 5 320 | 0,94 | 0,49 |
| `lib/util.mjs` | 7 787 | 208 | 2 | 89 | **7 787** | 6 061 | **1,00** | 0,81 |
| `docs/architecture.md` | 7 635 | 158 | 2 | 12 | **7 635** | 6 812 | **1,00** | 0,83 |
| `index.mjs` | 6 383 | 101 | 1 | 39 | **6 383** | 5 253 | **1,00** | 0,85 |
| `package.json` | 1 968 | 55 | 2 | 4 | **1 968** | 1 968 | **1,00** | 1,00 |
| **Итого** | **102 108** | | | | **80 613** | **56 112** | | |

Читается это так. Окно окупается там, где файл большой, а правка точечная: `lib/profile.mjs` —
363 строки, один хунк на две строки, 14 734 → 5 482 символа (−63 %) уже при ±80. И окно **не
даёт ничего** там, где хунков много или они широкие: у `lib/util.mjs` два хунка на 89
добавленных строк в файле из 208 строк — окна ±80 покрывают файл целиком, экономия ровно ноль,
`windowFileEntry` возвращает исходную запись. То же у `index.mjs`, `docs/architecture.md`,
`package.json` — **четыре файла из девяти при ±80 не экономят ни байта**. Промежуточный случай —
`lib/config.mjs`: 4 хунка, разбросанных по 449 строкам, окна ±80 покрывают 80 % файла, экономия
21 %; вырезаются три дырки, каждая помечена маркером пропуска, и за 4 700 сэкономленных символов
модель получает файл с тремя разрывами.

Вывод, который отсюда следует и который определяет дефолт: **широкое окно платит риском там,
где не даёт выигрыша**. Файл, который целиком помещается в пару окон, надо отдавать целиком —
это и дешевле по риску, и не дороже по токенам.

### 2. Дефолт: ±40 строк, файлы до 8 000 символов — целиком

Свип по уникальному контексту (`104 761` символ базы, девять файлов + 26 маркеров):

| Порог «целиком» | ±40 | ±60 | ±80 | ±120 |
|---|---:|---:|---:|---:|
| нет | 58 765 (−44 %) | 74 269 (−29 %) | 83 266 (−21 %) | 93 074 (−11 %) |
| 6 000 симв. | 58 765 (−44 %) | 74 269 (−29 %) | 83 266 (−21 %) | 93 074 (−11 %) |
| **8 000 симв.** | **62 444 (−40 %)** | 75 382 (−28 %) | 83 266 (−21 %) | 93 074 (−11 %) |
| 10 000 симв. | 62 444 (−40 %) | 75 382 (−28 %) | 83 266 (−21 %) | 93 074 (−11 %) |

**Решение: `margin = 40`, порог `8000` символов.** Обоснование по числам, а не по осторожности:

- ±80 — дефолт verifier'а — здесь даёт −21 % и при этом на четырёх файлах из девяти не
  экономит вообще. Наследовать его «за компанию» значит взять весь риск усечения ради пятой
  части экономии;
- ±40 даёт −40 % при пороге 8 000. Разница между ±40 и ±60 — 13 пунктов экономии, между ±60
  и ±80 — ещё 7; кривая заметно выполаживается после ±40, дальше платим токенами без отдачи;
- порог 8 000 символов (≈ 200 строк) возвращает 3 679 символов — 3,5 % контекста — и покрывает
  ровно те четыре файла, где окна ±80 не сэкономили ни байта. Это самая дешёвая страховка в
  предложении: она снимает целый класс «маленький файл, плотные правки», в котором усечение —
  чистый риск без выигрыша;
- почему не порог 10 000 или 12 000: на этом наборе 10 000 не меняет ничего (следующий файл —
  11 085), а 12 000 стоит уже 6,5 % контекста. Порог должен отсекать «файл целиком помещается в
  несколько окон», а не «файл среднего размера».

Разные значения у advisors (40) и verifier'а (80) — не рассогласование, а разные задачи:
verifier центрируется на конкретной строке-кандидате и обязан подтвердить или опровергнуть
одно утверждение, advisors обходят все правки файла и получают столько же контекста суммой
многих окон.

**Эффект на весь прогон.** При неизменной нарезке чанков: контекст 418 880 → ≈ 249 700 символов,
то есть **−169 тыс. символов ≈ −42k токенов ≈ −9,3 % всего входа прогона**. Замер с
пересчитанной нарезкой дал больше — 1 823 274 → 1 533 226 (−15,9 %), 33 вызова → 26 — но эту
разницу в отчёт брать нельзя: она возникла оттого, что уменьшенный контекст иначе упаковал
файлы по чанкам и два чанка перестали содержать исполняемые файлы (правило 2 RFC 04). Это
побочный эффект упаковки, он неустойчив и на другом PR может смениться на противоположный.
**Заявляемая величина — 9,3 %.**

И честная оговорка о репрезентативности: `pr-6.patch` — **худший случай** для этого решения.
26 из 35 файлов добавлены (уже маркеры), а из девяти оставшихся четыре правятся плотно.
На PR, где меняют по паре строк в больших существующих файлах, экономия ближе к профилю
`lib/profile.mjs` (−63 %). Нижняя граница здесь измерена, верхняя — нет.

### 3. Промпт: снять обещание и включить запрет отсутствия

Три текстовые правки, **синхронно в JS и Rust** — это контур паритета
`rust/parity/prompt.parity.mjs`.

**(а) Системный промпт агрегатора** ([`lib/prompt.mjs:316`](../lib/prompt.mjs) /
[`rust/src/prompt.rs:255`](../rust/src/prompt.rs)). Фраза
`you have the FULL content of the changed files (not only the diff)` заменяется на
формулировку, которая описывает то, что реально приложено, и **сразу закрывает вывод об
отсутствии**: приложены окрестности изменённых участков файлов, пропуски помечены
`… (строки N–M пропущены)`, и пропуск — это «не показано», а не «не существует». Требование
«USE this to RESOLVE your doubts» остаётся: оно про то, чтобы не оставлять вопросов там, где
ответ виден, и от размера контекста не зависит.

**(б) Заголовок секции** ([`lib/prompt.mjs:331`](../lib/prompt.mjs) /
[`rust/src/prompt.rs:583`](../rust/src/prompt.rs)) перестаёт быть `Full content of changed
files` и называет вещь своим именем — контекст изменённых файлов, окна вокруг изменённых
участков. **То же самое в промпте verifier'а** ([`lib/prompt.mjs:404`](../lib/prompt.mjs) /
[`rust/src/prompt.rs:536`](../rust/src/prompt.rs)) — там заголовок врёт уже сегодня.

**(в) Анти-absence-правило перестаёт зависеть от `split`.** В
`buildChangedFilesSectionJs` ([`lib/prompt.mjs:417-465`](../lib/prompt.mjs) /
[`rust/src/prompt.rs:381-443`](../rust/src/prompt.rs)):

- чанк получает новое поле `windowedPaths: string[]` — пути, у которых контекст урезан окнами;
- в карте PR такой путь метится **третьей** меткой — `[THIS PART, CONTEXT WINDOWED]`, а не
  `[THIS PART, SOME HUNKS ONLY]`: у него все хунки на месте, урезан только текст между ними, и
  подменять один факт другим нельзя;
- `split` становится истинным и когда `windowedPaths` непусто — иначе PR из одного чанка с
  окнами не получит `HARD RULE — NO ABSENCE CLAIMS` вовсе;
- в текст правила добавляется строка про окна: нельзя утверждать, что символ/вызов/обработка
  **отсутствует** в файле, чей контекст помечен как оконный, — маркер `… (строки N–M
  пропущены)` доказывает, что часть файла не показана. Кросс-файловый и внутрифайловый риск
  по-прежнему можно поднять как риск с `confidence ≤ 0.5`.

`partialPaths` при этом **не трогается**: у него свой смысл (файл разрезан между чанками), свой
источник ([`lib/diff.mjs:428`](../lib/diff.mjs)) и свой единственный читатель.

`windowedPaths` **не добавляется в `buildChunks`** и потому не требует правки Rust-порта
нарезки: окна ставит `pipeline.mjs`, он же и знает список — поле дописывается в объекты чанков
сразу после `buildChunks`. Меньше поверхности для молчаливого рассинхрона сторон.

### 4. Где в пайплайне стоит окно

Порядок — это и есть решение; перепутанный он ломает две вещи молча.

```
pipeline.mjs:408   collectBlastSymbols(changedText, contentMap, …)   ← ПОЛНАЯ карта
pipeline.mjs:~410  windowedMap = windowChunkFileContents(contentMap, files, limits)   ← НОВОЕ
pipeline.mjs:453   fileInputHashes(changedPaths, diffSections, windowedMap)
pipeline.mjs:482   contextForLlm = фильтр windowedMap по incrementalPlan.reviewPaths
pipeline.mjs:490   buildChunks(annotatedForLlm, contextForLlm, limits)
pipeline.mjs:189   buildVerifierFileContents(contentMap, candidates, …)  ← ПОЛНАЯ карта, как сейчас
```

- **После `collectBlastSymbols`**: он добирает экспорты из полного текста, и `export function`
  в начале файла не попадает ни в одно окно вокруг хунков в конце. Окно раньше — тихо пустой
  blast-radius, то есть потеря детерминированного сигнала ради экономии на вероятностном;
- **до `fileInputHashes`**: RFC 05 определяет единицу сравнения как вход модели. Хэш от окна
  самоинвалидируется при смене `margin` — файл, который в прошлом прогоне ехал с ±40, а в этом
  поедет с ±60, честно считается изменившимся и переревьюивается. Хэш от полного файла этого не
  заметил бы, и пришлось бы дописывать `margin` в `configFingerprint`
  ([`lib/incremental.mjs:72`](../lib/incremental.mjs)), что сбрасывало бы состояние целиком
  вместо пофайловой инвалидации. Правка `configFingerprint` этим RFC не нужна и не делается;
- **verifier получает по-прежнему полную `contentMap`** ([`pipeline.mjs:189`](../pipeline.mjs)).
  Двойное окно (вокруг хунков, потом вокруг строки кандидата) дало бы пересечение двух
  вырезок, и находка, поставленная на строку вне хунков, осталась бы без контекста именно в тот
  момент, когда решается блокировать ли merge. Второй проход — единственный читатель, которому
  разрешено резать самому, потому что он знает, вокруг чего.

### 5. Контракты

```js
// lib/context-window.mjs — рядом с buildVerifierFileContents, тот же windowFileEntry внутри
/**
 * Контекст изменённых файлов для advisors и жюри: в каждом файле — окна ±margin вокруг
 * строк, которые PR трогает. Файл короче minChars отдаётся целиком.
 * @param {Map<string,string>} contentMap записи readChangedFiles
 * @param {Map<string,{validLines:Set<number>}>} files карта parseDiff (центры окон)
 * @param {{margin:number, minChars:number}} opts  margin=0 → окна выключены, карта возвращается как есть
 * @returns {{ map: Map<string,string>, windowed: Set<string>, before: number, after: number }}
 */
export function windowChunkFileContents(contentMap, files, { margin = 40, minChars = 8000 } = {})
```

`windowed` — это и есть источник `windowedPaths` для карты PR; `before`/`after` идут в лог и в
событие `plan` тем же способом, каким это уже сделано для verifier'а
([`pipeline.mjs:195`](../pipeline.mjs)).

Конфигурация — в `limits`, рядом с соседями по RFC 04
([`lib/config.mjs:398-404`](../lib/config.mjs) и зеркало
[`rust/src/config.rs:833-837`](../rust/src/config.rs)):

| Переменная | Default | Смысл |
|---|---|---|
| `REVIEW_CONTEXT_MARGIN` | `40` | ±строк вокруг изменённых строк файла в контексте advisors и жюри. **`0` — окна выключены**, файлы едут целиком (это и есть откат) |
| `REVIEW_CONTEXT_WINDOW_MIN_CHARS` | `8000` | файл короче этого прикладывается целиком, окна не считаются |

`0` означает «выключено», а не «окно нулевой ширины»: при нуле `windowFileEntry` не вызывается
вовсе. Это надо написать в коде явно — «margin=0» иначе читается как «оставить только сами
изменённые строки», ровно наоборот по смыслу.

**Файлы, которые меняются при реализации:** `lib/context-window.mjs` (новая функция),
`pipeline.mjs` (вызов + `windowedPaths` + лог + поле в `plan`), `lib/config.mjs` и
`rust/src/config.rs` (две переменные, паритет `rust/parity/config.parity.mjs`),
`lib/prompt.mjs` и `rust/src/prompt.rs` (три текстовые правки + метка + условие `split`,
паритет `rust/parity/prompt.parity.mjs`), `docs/configuration.md` (две строки таблицы),
тесты. Нарезка чанков (`lib/diff.mjs`, `rust/src/bin/diff.rs`) не меняется.

## Миграция

Флаг с дефолтом «включено» — как решения 1–4 RFC 04, и по той же причине: экономия здесь не
меняет наблюдаемого контракта с потребителем (ни формата sticky, ни отпечатков, ни артефакта
экспорта), а меняет только вход моделей. Откат — `REVIEW_CONTEXT_MARGIN=0`, одна переменная,
без миграции состояния.

Инкрементальное состояние прошлых прогонов инвалидируется само: хэши считаются по оконному
контексту, у файлов они изменятся, и первый прогон после включения будет полным по этим файлам.
Отдельного шага миграции не нужно.

**Гейт мержа реализующего PR — тот же протокол, что у RFC 04:** зелёный `npm run eval`, затем
gold-прогон; шаг, ухудшивший recall, откатывается, а не «донастраивается».

## Риски и что не делаем

- **Риск (главный): утверждение об отсутствии по усечённому виду.** Модель не видит вырезанный
  кусок и пишет «валидации нет», «функция нигде не вызывается», «обработка ошибки отсутствует».
  Смягчение — решение 3 целиком: правило `NO ABSENCE CLAIMS` включается при непустом
  `windowedPaths` (в том числе на однокусочном PR, где сегодня его нет вовсе), метка
  `[THIS PART, CONTEXT WINDOWED]` стоит в карте PR, маркеры `… (строки N–M пропущены)` стоят в
  самом контексте. Наблюдаемая проверка — gold-кейсы
  `fp-absence-consumer-out-of-chunk` и `fp-absence-doc-claims-not-in-diff`: у обоих в `expect`
  лежит `mustNotFindTitles` (`«consumer не в диффе»`, `«которых нет в diff»`) и
  `wouldBlock: false`. Всплывший absence-класс на этих двух кейсах — **сигнал остановки**, а не
  повод править формулировку правила в третий раз.
- **Риск: объявление за окном.** Правку в конце длинной функции окно ±40 отрежет от её
  сигнатуры и от инициализации переменных выше. Это плата за решение, и она частично
  компенсирована: git даёт три строки контекста вокруг каждого хунка **в самом диффе**, а дифф
  не режется никогда и составляет 60 % входа. Наблюдаемая проверка — recall на
  `tp-real-bugs-unescape` (`mustFindLocations`: `lib/diff.mjs` строки 5–6 и 9–10) и
  `tp-structure-real-defects` (4 размеченные локации, база — 2 из 4). Потеря найденной локации
  — сигнал остановки.
- **Риск: рост ложных блокеров.** Контроль — `fp-noise-no-real-blockers` с `wouldBlock: false`;
  переход ✅ → ❌ на нём отменяет решение (прецедент: эксперимент A5 в RFC 04 был отклонён
  ровно по этому кейсу).
- **Что смотреть в JSONL, кроме gold.** `plan.chunkPlan[].context_chars` — сколько контекста
  реально уехало по чанкам; `llm_call.prompt_chars` в разрезе `callType`
  `specialist`/`advisor`/`moa_aggregate` — где именно упал вход (у `callType: 'verifier'`
  этого поля нет, RFC 04 это уже зафиксировал); `run_end.efficiencyMetrics.tokens_per_inline`
  и `tokens_per_blocker` ([`lib/cost.mjs:81`](../lib/cost.mjs)) — знаменатель тут находки,
  доехавшие до человека, и решение имеет смысл ровно пока эти две величины падают или стоят.
  Экономия входа при выросшем `tokens_per_inline` означает, что сэкономили на находках, а не
  на словах.
- **Риск: пустой blast-radius.** Снимается порядком (решение 4): окна ставятся после
  `collectBlastSymbols`. Тест обязателен — «символы blast-radius те же с окнами и без».
- **Не делаем:** не режем дифф. Он и есть предмет ревью, и 60 % входа — это его законная доля.
- **Не делаем:** не трогаем `REVIEW_MAX_FILE_LINES` (1500) и `REVIEW_MAX_CONTEXT_BYTES`
  (180 000): это верхние отсечки против гигантских файлов, у них другая задача, и окна их не
  заменяют.
- **Не делаем:** не окно для verifier'а второй раз и не сводим два `margin` в один параметр —
  у них разные центры и разные задачи.
- **Не делаем:** не строим «умное» окно по AST/символам (взять объявление функции целиком,
  дотянуть импорты). Такой контекст — задача Graphify и blast-radius, отдельного контура с
  собственными доказательствами, а не параметра `margin`.
- **Не делаем:** не трогаем `partialPaths`, `resolveBlockers`, `REVIEW_BLOCK_ON`, веса
  `actionability`, формат футера sticky и `EXPORT_VERSION` — контракт с потребителем не
  меняется.

## Оценка

| Шаг | Задач | Что входит |
|---|---:|---|
| `windowChunkFileContents` + подключение в `pipeline.mjs` в правильном порядке | 1 | функция, лог, `context_chars` в `plan`, тест «символы blast-radius не изменились», тест «хэш инкрементальности считается по окну» |
| Две переменные конфигурации в JS и Rust | 1 | `lib/config.mjs`, `rust/src/config.rs`, паритет, `docs/configuration.md` |
| Промпт: снятое обещание, честные заголовки (включая verifier), метка и `split` по `windowedPaths` | 1 | `lib/prompt.mjs` + `rust/src/prompt.rs`, паритет `prompt.parity.mjs`, тест «однокусочный PR с окнами получает `NO ABSENCE CLAIMS`» |
| Замер | 1 | `npm run eval` + gold на пяти кейсах: `tp-real-bugs-unescape`, `tp-structure-real-defects`, `fp-noise-no-real-blockers`, `fp-absence-consumer-out-of-chunk`, `fp-absence-doc-claims-not-in-diff`; таблица «до/после» дописывается в этот RFC |

**Ожидаемый эффект на `pr-6.patch`:** контекст файлов 418 880 → ≈ 249 700 символов (−40 %),
весь вход прогона −9,3 % при неизменной нарезке. На PR с точечными правками больших файлов —
существенно больше; измеренная здесь величина является нижней границей.

## Замер реализации (тот же `pr-6.patch`, gold не входит)

Прогнан на реализованном коде, скриптом замера, без LLM. База выросла со 104 761 до 107 455
символов не от решения, а от самого реализующего PR: `readChangedFiles` читает **рабочий
каталог**, а `lib/config.mjs`, `lib/util.mjs`, `index.mjs` и `docs/configuration.md` входят в
девятку изменяемых файлов и в этом PR подросли.

| Величина | Без окон (`REVIEW_CONTEXT_MARGIN=0`) | С окнами (±40, порог 8 000) | Δ |
|---|---:|---:|---:|
| Уникальный контекст изменённых файлов | 107 455 | **64 090** | **−40,4 %** |
| Контекст, оплаченный по всем вызовам (нарезка неизменна) | 429 656 | 256 196 | −40,4 % |
| Доля от всего входа прогона (нарезка неизменна) | — | — | **−9,4 %** |
| Файлов, реально урезанных окнами | 0 | 6 из 35 | |

Предсказание RFC — 62 444 символа (−40 %) — сбылось: расхождение с 64 090 объясняется
центрами окон. Свип считался по `+`-строкам, а решение 1 задаёт центрами `validLines`, куда
входят и контекстные строки хунка, то есть окно шире на три строки с каждой стороны каждого
хунка. Контрольный пересчёт по методике свипа на сегодняшнем дереве даёт 61 888 — реализация
дороже его на 2 202 символа (3,4 %) и настолько же честнее: `validLines` — то, что PR
действительно трогает, и именно эта величина уже является единицей сравнения в RFC 05.

Замер с **пересчитанной** нарезкой даёт больше (1 841 432 → 1 539 840, −16,4 %; 33 вызова →
26), но в отчёт эта величина не берётся по причине, названной в решении 2: уменьшенный
контекст иначе упаковал файлы по чанкам, два чанка перестали содержать исполняемые файлы, и
эффект неустойчив. **Заявляемая величина — −9,4 % входа прогона.**
