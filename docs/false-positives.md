# Ложные срабатывания: семейства, защиты, цикл обучения

Ложный блокер стоит дороже пропущенного замечания: один раз обойдя красный гейт «потому что
он врёт», команда перестаёт ему верить совсем. Поэтому FP здесь — не мелочь, а отдельный
контур: известные семейства ошибок, встроенные защиты и петля обучения на реальных PR.

Журнал конкретных случаев ведётся **в репозитории-потребителе** (`paths.fpMarkdown` профиля):
он про его код и его PR. Здесь — то, что переносится между проектами.

## Семейства FP (наблюдения на реальных прогонах)

1. **«Файла/теста нет в PR» — при том, что он в диффе.** Модель комментирует строки файла,
   то есть видит его, но в выводе пишет «изменений в `X` нет». Классика при разрезании
   большого PR на части: чанк с UI не видит чанк со спекой и заявляет «e2e нет».
2. **Сходимость превращается в накопление.** Прошлые находки подмешиваются в промпт, и модель
   переутверждает их, не сверяясь с уже внесённым фиксом; число блокеров растёт от прогона к
   прогону (1 → 3 → 4). «Запушить фикс и перепрогнать» делает хуже.
3. **Фикс в соседнем коммите «теряется».** Замечание раскрыто одним коммитом, фикс — следующим;
   инкрементальный дифф их не коррелирует, находка повторяется.
4. **Гипотеза несуществующего кода.** Модель предполагает серверную логику, которой по дизайну
   нет, и требует «обновить сервер».
5. **Устаревшие знания вместо кода.** «Версии `actions/checkout@v6` не существует»,
   «это синтаксическая ошибка ESM» — утверждения об окружении, а не о показанном коде.
6. **Critical о том, чего модель не видела.** «Невозможно проверить устранение находок в
   `Main.tsx`» — файл просто не попал в её часть PR. Самоопровержимая находка.
7. **«Файла/модуля нет» о файле вне PR.** Модель видит `import … from './helpers'`, файла
   `helpers` нет ни в диффе, ни в контексте чанка — и пишет «импорт несуществующего модуля».
   Файл в репозитории есть, он просто не менялся. Защиты семейств 1/6 тут не помогают: в
   списке изменённых файлов его и не должно быть.

## Что движок делает против этого

| Защита | Против чего |
|--------|-------------|
| Полный список изменённых файлов в КАЖДОМ чанке + метки `[THIS PART]` / `[ANOTHER PART]` | 1, 6 — запрет заявлять отсутствие того, что видно в списке |
| Список e2e-спек PR отдельным блоком (`layout.e2eSpec` профиля) | 1 — «тестов нет» при спеке в диффе |
| Отпечаток кода у перенесённой находки: код изменился → находка снимается | 2, 3 |
| Δ-блок и история прогонов в sticky | 2 — расхождение видно сразу, а не на четвёртом прогоне |
| Правила проекта из профиля (слои, канонические примитивы) | 4 — меньше догадок об архитектуре |
| Явные запреты в промпте: версии инструментов, «синтаксическая ошибка», «символ не определён» | 5 |
| Refutation жюри + verifier Pass B | все — блок требует подтверждения второй моделью |
| FP-паттерны (`fp-patterns.jsonl`) | 1, 5 — известные формулировки гасятся до постинга |
| Сверка с деревом репозитория ([`lib/absent-path.mjs`](../lib/absent-path.mjs)) | 7 — см. ниже |
| Auto-triage тредов с известным FP | шум на PR: тред закрывается сам, с объяснением |

Снятые паттернами находки не пропадают молча — они видны в sticky отдельной свёрнутой
секцией: слишком широкий паттерн иначе тихо проглотил бы верное замечание.

## Семейство 7: сверка с деревом репозитория

Регексом это семейство не закрыть: «модуля нет» бывает и правдой (PR удалил файл, а импорт
остался). Решает не формулировка, а дерево. После LLM, в том же FP-фильтре, что и паттерны,
находка снимается, если одновременно:

1. в одном предложении стоит утверждение об отсутствии файла/модуля («не существует»,
   «не найден», «несуществующий модуль», `Cannot find module`, `does not exist`) **вплотную**
   к упомянутому пути;
2. путь разрешается в файл дерева: относительный — от каталога файла находки, с перебором
   расширений и `index.*`; алиас `@/`, `~/` и путь с «/» — по суффиксу; голое имя — только
   в каталоге находки.

Не снимается:

- отсутствие как условие рантайма — «если `config.json` не существует, упадём», `ENOENT`,
  `existsSync`: это находка о коде, а не о дереве;
- отсутствие символа в существующем файле — «экспорт `parse` не найден в `a.ts`»: путь
  есть по условию, проверять надо содержимое, а не дерево;
- путь, которого в дереве нет, — находка верная.

Дерево — `git ls-files` рабочего каталога (тот же checkout, из которого читается контекст),
в тестах — `deps.repoFiles`. Если git недоступен или дерево явно чужое — меньше половины
изменённых путей PR в нём есть (локальный `--dry-run --diff` из другого каталога), —
индекса нет, и фильтр работает как раньше, только паттернами. Снятая находка попадает в ту
же свёрнутую секцию sticky, что и снятые паттернами, причина — в логе прогона.

## Стартовый набор паттернов

В пакете лежит [`feedback/fp-patterns.jsonl`](../feedback/fp-patterns.jsonl) — паттерны,
переносимые между проектами (e2e-в-диффе, файл-в-диффе, версии GitHub Actions). Каждый
ограничен по путям, поэтому безопасен и в чужом репозитории. Свои паттерны потребитель
держит у себя и указывает через `paths.fpPatterns` профиля.

Формат строки:

```json
{"id":"e2e-in-diff","description":"…","regex":"…","requiresPath":"(?:^|/)e2e/.*\\.spec\\.ts$","matchChangedBasename":false}
```

`regex` проверяется по тексту находки, `requiresPath` — по изменённым путям PR,
`matchChangedBasename` требует, чтобы в тексте встретилось имя файла из диффа. Регексы
ограничены по длине и отбраковываются по признаку катастрофического бэктрекинга.
